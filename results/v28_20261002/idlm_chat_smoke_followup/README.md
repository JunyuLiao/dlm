# I-DLM official chat protocol follow-up

Run002 completed three toy calls with exit code0 on one H10080GB. All three contained the expected answer substring, but every call reached the512-token length limit. This confirms environment execution and answer presence only. Natural stopping and final-answer quality remain unqualified. No raw prompt, output, expected-answer literal, or stop-token IDs are published. Run001 and its published report remain unchanged.

The follow-up used the original model chat template with tokenization and an assistant generation prompt, preserving the official default thinking mode. It used the original generation-config EOS list and native EOS behavior with ignore_eos disabled. The prompt contained23tokens. The earlier raw prompt contained15tokens and had a64-token cap; the official inference README chat example uses512. Both format and budget changed, so this is not a causal isolation experiment. Their correction did not eliminate length stopping.

Sampling precedence is now source-verified. The pinned IDLMBlockN implementation reads temperature/top-k/top-p from the algorithm configuration and calls its sampler with those instance fields. Request sampling does not override them. Both runs therefore used algorithm temperature1, top-k50, top-p0.95; the follow-up aligned the request fields with those values. Request length and EOS settings still govern stopping. The request finish checker checks the length cap before EOS, so a length result alone cannot exclude an EOS occurring at the cap. See the source evidence links in summary.json.

The follow-up reserved190.277685GPU seconds, including loading, graph capture, JIT, generation, and teardown. The first call included135.639968seconds of initial JIT/execution. The two I-DLM attempts total377.484967GPU seconds; all new-model attempts total723.034485GPU seconds. The GPU was released to zero used MiB and zero utilization. These timings are qualification costs, not benchmark measurements.

The internal algorithm contains a cumulative total-forwards counter, but Engine.generate does not expose a verified per-request count and coverage of graph capture/general model calls is unverified. The pure-prefill path does increment the internal counter. No instrumentation patch or algorithm change was added. The previously recorded annotation-only Python3.10 compatibility line remains the sole source adjustment.

The requested think-closure, repetition, and actual-output EOS diagnostics are unavailable for the completed runs: only metadata was retained, and the workers have exited. This limitation is recorded with null metrics, rather than inferred values. No new GPU call was made for diagnosis.

Stop plumbing was checked in the pinned source. Submitted stop values exactly match the original model generation configuration; SamplingParams preserves membership while converting the list to a set. The reviewed DLLM output paths append one committed token and run the finish check after each token. CPU synthetic tests recognize both model EOS values at positions 1, 100, and 511; position 512 reports length because the cap takes precedence. These checks show no evident stop-set mismatch or skipped-block finish check, but cannot establish the actual real-worker output tokens or live request state.

The project README uses a 4096-token proof example, while the inference README uses 512 for a toy chat and describes 2048 for its benchmark. Neither README chat example sets enable_thinking=False. The model template supports that switch, but this run preserved the official default. The retained evidence cannot distinguish continued or repetitive thinking from another generation integration issue. An unqualified model baseline must not be counted as accuracy loss caused by a proposed sparse method.
