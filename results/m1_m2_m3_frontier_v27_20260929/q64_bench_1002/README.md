# q64 / q64r / split-KV kernel bench on identical real states (2026-10-02)

**Question:** can the regrouping line (64-row maps, row regrouping, FA4 kernel settings) be made faster? This is a
kernel-level measurement only; the end-to-end test is the E14 panel.

**Method** (`scripts/v27_q64_bench.py`, run on dllm in the E13 deploy `v27_e13_4552f78`).
- Real requests: LongBench-v2 32K / 64K / 96K items 0–3, seed 404, generated by the E13 q64 arm.
- At every dense-prefix decision, the route's risk state is kept. At the first FA4 call of that decision, the same
  Q/K/V are timed under every map below. The timed outputs are discarded, so generation is untouched.
- 60 decisions per request, 240 per bin.
- Timing: CUDA events, 2 warm-ups, then the median of 15 interleaved rounds in rotated order.
- **Maps.**
  - `128`: the executed M3 map.
  - `q64`: the same worst-row rule per 64-row half.
  - `q64r`: rows sorted by need count within each 128-row block, then cut into 64-row groups. Includes the Q gather
    and the output scatter. The idea is credited to chw/value_aware; the bench uses an inline copy of
    `_regroup_q64` from commit 02fb86c, because E13's frozen configs pin E13's source.
  - Each map runs at FA4 `num_splits` 1 and 2. Dense all-kept is the reference.

**Medians per bin (240 decisions each).** Times are ms for one GLOBAL layer call (256 queries, 16 heads, hd 512).

**Reading.**
- **q64 cuts the sparse GLOBAL call by 9–11%.** It skips about a quarter of the kept prefix tiles. The time drops
  less than the tile count because each call has fixed costs. The extra per-decision refinement (about 0.1 ms) runs
  on the side stream of the asynchronous route.
- **Regrouping (q64r) is not worth it on FA4.** It removes only another 4–6% of the kept tiles. The Q permutation,
  the output scatter and a slower kernel on the gathered layout cost more than that: q64r is 11–13% slower than q64
  and no faster than the 128-row map.
  - A layout-preserving gather might reach about parity with q64. That is an estimate, not measured: the tile saving
    of about 5% is roughly the 0.024 ms permutation cost.
  - Regrouping would need row indirection inside the kernel to pay off, which the official FA4 interface does not
    offer.
- **FA4 split-KV does not help sparse calls either.** `num_splits=2` is 4–5% slower on every map, even though the
  per-CTA work is imbalanced (max/mean kept tiles 1.7–2.2). This matches the dense result in
  `official_baseline/README.md`.
- Outputs agree across settings: `num_splits` 2 vs 1 differs by 0.0. The worst single-element deviation from dense
  is similar for the 128-row and q64 maps (same per-row rule); accuracy is judged in the panels, not here.
- **Consequence for E14:** run q64 plus the 64-row carried call-0 map (`q_carry64`, q64c). In E13 that call still
  used 128-row lists. Do not run q64r or split-KV.
