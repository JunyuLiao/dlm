# 本周进展（2026-09-30）：DiffusionGemma 上的 Fan M1/M2/M3 稀疏注意力

四页组会汇报的内容草稿。数字均来自本目录下已推送的结果，每条后面标了出处。标"待出"的两项今天跑完后补上。

## 第 1 页：公平的实验设置与最强基线

**设定**
- 模型：DiffusionGemma-26B-A4B，使用官方生成配置（置信度 0.005、stability 1、每个 canvas 最多 48 步、canvas 长 256），即原生自适应停止。
- 硬件：单卡 H100 80GB。

**Dense 基线：用官方里最快的 FA4**
- 基线是官方 FlashAttention-4（vLLM flash-attn cute）。FA4 的 block-sparse 接口在全部保留时，与 FA4 dense 逐位一致，而且快 1–2%。
- HF 默认走的 PyTorch SDPA 在 head_dim 512 下，kernel 慢 5.8–7.5 倍，端到端慢 1.6–2.2 倍。如果拿它当基线，加速会被夸大。
- 出处：`kernel_bench/`、`fa4_panel_v3/`。

**所有方法共用同一执行底座**
- 做法：分段 CUDA graph（vLLM 式），加上 FA4 prefill 和 canvas 追加。
- 顺带修掉了官方实现的一个低效之处：每一步都把整个 encoder KV 重新拼接一遍。修复后生成的 token 逐位不变，所有方法的 64K 请求都快 5–6%。
- 出处：`substrate/`。

**稀疏方法与 dense 的唯一区别是跳过了哪些块**
- 所有稀疏方法都跑在同一个 FA4 block-sparse kernel 上。
- 协议在生成前冻结；同一题的所有方法在同一台机器上跑；比值是和 dense 在同一题同一 seed 上配对的几何平均，置信区间按题目聚类 bootstrap。
- 每个变体都从运行记录里核对过确实走了预期的代码路径。

## 第 2 页：主结果：长上下文有端到端加速，短上下文没有

**LongBench-v2 64K 区间（56–76K tokens，12 题 × 3 seed = 36 格，与 dense FA4 配对）**

| 方法 | 请求时间 [95% CI] | 去掉 prefill 的解码时间 | 答对（dense 18） |
|---|---|---:|---:|
| M3 R6 DP，阈值 −ln2 | **0.872×** [0.812, 0.936] | **0.783×** | 23 |
| B（每个 canvas 观测一次后固定 map） | **0.861×** [0.821, 0.903] | **0.788×** | 20 |
| Fan 原版 M1 / M2c / M3（A8） | 1.27× / 1.50× / 1.12× | 1.42× / 1.79× / 1.18× | 20 / 16 / 21 |

- 两个最佳配置在阈值扫描和变体面板、两套底座上都复现了（0.866→0.861，0.868→0.872）。出处：`variants_v5/`、`threshold_sweep_s1/`。

**32K 区间（28–40K）**
- 请求级没有显著加速，最好的一档是 0.90–0.93×，置信区间跨过 1。

**短上下文**
- LongBench 标准池（10–19K）：稀疏版请求时间 1.08–1.29×，比 dense 慢。
- AIME（60 格）：不加长度门限时，所有稀疏方法都是净减分，其中 B 显著（26 vs 35，p = 0.049）。
- 加 8K 长度门限后，AIME 走 dense，精度与 dense 完全一致。出处：`quality_panel_q1v3/`。

**待出：最终配置全面板**
- 8 个方法（dense、Fan 原版 M1/M2c/M3、B、M3 R6 DP −ln2，后两者各有一个 32K 长度门限版）。
- 数据：AIME 30 题 × 4 seed、LongBench 标准池与 32K/64K 各 3 seed。

## 第 3 页：为什么 kernel 快 7 倍，端到端只快约 1.15 倍

**三层加速（64K，保留约 10% 的块）**

| 层级 | 加速 | 说明 |
|---|---:|---|
| kernel（FA4 block-sparse vs FA4 dense，真实 GLOBAL 层形状） | 7.3× | 32K 为 5.9×，128K 为 8.3× |
| 注意力模块（真实请求里，含每个 canvas 的 dense 首步、观测和决策） | B 4.4×；M3 R6 DP −ln2 2.7× | |
| 端到端 | 请求 1.15×；去掉 prefill 后解码 1.27× | GLOBAL 注意力只占 dense 64K 请求时间的 14%（32K 为 9%） |

- **Fan 原版在注意力模块这一层就比 dense 慢（0.3–0.7×）。** 它的逐块顺序选块每次 2.3–7.9 ms/层，比 dense 注意力本身（1.5–3 ms）还贵，而且每 8 步重算一次完整 QK。
- **我们的变体去掉了这部分开销：** 每个 canvas 只做一次融合观测，dense-prefix 决策只要 0.27 ms，选块放在侧流异步执行，决策之间沿用上一次的 map。出处：`kernel_bench/`。
- **请求时间的构成（dense，32K）：** prefill 39%，decoder forward 41%，其中 GLOBAL 注意力 9%、LOCAL 注意力约 1.5%，其余是 MoE 等。LOCAL 窗口只有 1024，跳过 LOCAL 最多省 2.4%，实测反而更慢。出处：`substrate/time_breakdown.json`。
- **自适应停止下，越稀疏步数越多。** 阈值越激进，单次调用越便宜，但每个 canvas 的去噪步数增加（+ln2 时 +40%）。所以端到端最优点是 −ln2，而不是最稀疏的那一档。出处：`threshold_sweep_s1/`。

## 第 4 页：新颖性现状、负结果与下一步

**已有工作（撞车检查）**

| 工作 | 做法 | 与我们的关系 |
|---|---|---|
| SparseD（ICLR 2026） | 前 20% 的步用 dense，之后按块平均注意力分数选一次模式（保留 30%）并一直复用；固定步数 | ≈ 我们的 B |
| PulseCol（2026） | 在少数中间步刷新稀疏模式 | ≈ M3 的思路 |
| FlashBlock（2026） | 块扩散中跨步复用前缀注意力输出；针对 4–8 token 的小块 | 在 256-token 的 canvas 上几乎不会触发复用 |
| BA-Att（2026） | 块近似稀疏注意力 | — |

**可能的新意（都需要数据支撑）**
1. **Fan 的选块会看 V：** 用 QK 加投影后的 V 估计"跳过这个块会让输出变多少"，而 SparseD 只看注意力分数。同一 FA4 kernel、同等稀疏度下的正面对比面板已冻结，正在排队。
2. **自适应停止下的设定：** 稀疏度会改变去噪步数，从而移动端到端最优点。已有工作都用固定步数，需读全文确认没人讨论过。
3. **基线更严格：** 对比 FA4（已有工作用 FlashAttention 或 Flex），并且 kernel、注意力模块、端到端三层都报。

**负结果（都有数据支撑）**
- 第一层或前两层 GLOBAL 保持 dense、canvas 到第 24 步后转 dense、按风险总预算选块：都没有超过简单的 −ln2 阈值。
- 按风险总预算选块，在同等保留比例下与逐块阈值覆盖的注意力相同，所以没有纳入。
- 跳过 LOCAL 层不值得做。

**下一步**
1. 汇总最终配置全面板（今天完成）。
2. SparseD 正面对比。若 Fan 的选块在同等速度下不优于 SparseD，按撞车处理，不硬凑正结果。
3. 补 RULER 32K/64K，以及 96–128K 更长上下文（GLOBAL 注意力占比更高）。
4. 降低观测开销：它是 kernel 加速与模块加速之间差距的主要来源。
