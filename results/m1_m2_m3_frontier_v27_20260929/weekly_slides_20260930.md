**本文统一的记号与口径**
- 比值 < 1 表示比 dense 快。
- W：请求墙钟时间。
- S：去掉 prompt prefill 之后的解码时间。
- 步数/canvas：每个 256-token canvas 的去噪调用数。
- "答对"：strict correct 的格数；"+a/−b"：只有该方法答对 / 只有 dense 答对的格数。
- 比值是配对后的几何平均，95% 置信区间按题目聚类 bootstrap（4000 次重采样）。
- 两两精度差异用配对符号检验（双侧）。
- 格：一个（题目, seed）组合；同一格的所有方法在同一块 GPU 上跑，比较都在机器内配对。
- Wc：同 W，但剔除计时期间捕获了新 CUDA graph 的配对（首次遇到新形状时单条请求会多出几秒到几十秒）。
- N：去噪步数（decoder 调用次数）比；T：输出 token 数比；S/N：每步平均解码时间比，是摊销值，不是单次 forward 的直接计时。
- 实际稀疏度：固定稀疏度面板里按构造算的、被跳过的 GLOBAL key 块占全部 GLOBAL 调用的比例（canvas 块总保留、每个 canvas 第一步 dense），不是逐块遥测。
- topk XX%：我们为固定稀疏度比较加的变体，用 M1-DP 风险给 prefix 块排序，每个（head, query 块）保留风险最高的 (1 − XX%)，其余同 M3 R6 DP。
- SparseD kXX sY（移植）：每个 canvas 前 Y 步 dense，然后按平均池化注意力分数保留 XX% 的 prefix 块并沿用到 canvas 结束；AIME 面板写作 SparseD sXX，XX 是目标稀疏度。
- 生成设置：thinking 开启，每个请求最多 8192 token；LongBench-v2 用 NeMo 多选评分器，AIME 精确匹配。
- 机器：dllm、mpk、dlm2 三块 H100 80GB；跨机器生成不能逐位复现，同一方法的答对数跨机器约差 ±3/36。

## 实验 1：基线选择与执行底座（公平性的前提）

**【正文顶部】** DiffusionGemma-26B-A4B · 原生自适应停止 · H100 · GLOBAL 层 head_dim 512 · 候选 dense：FA4 / FA4 全保留 / PyTorch SDPA（HF 默认）

**【主结果】**

| 一层 GLOBAL 注意力（256 个 canvas query） | 8K | 16K | 32K | 64K | 128K |
|---|---:|---:|---:|---:|---:|
| FA4 dense（官方 FlashAttention-4） | 0.443 ms | 0.787 ms | 1.504 ms | 2.862 ms | 5.616 ms |
| FA4 block-sparse API，全部块保留（**我们的 dense 基线**） | 0.441 ms | 0.766 ms | 1.410 ms | 2.691 ms | 5.273 ms |
| PyTorch SDPA（HF 模型默认路径） | 2.56 ms | 5.01 ms | 10.07 ms | 19.87 ms | 39.50 ms |

**端到端请求时间，HF SDPA 相对 FA4 全保留：**

| 数据 | 比值 [95% CI] |
|---|---|
| LB 64K | 2.19× [1.95, 2.44] |
| LB 32K | 1.92× [1.58, 2.27] |
| LB 标准池 | 1.64× [1.41, 1.90] |
| AIME | 1.01× [0.87, 1.13] |

**【要点】**
- 基线用官方实现里最快的 FA4。"全保留"与 FA4 dense 逐位一致，并快 1–2%。所有稀疏方法跑在同一个 FA4 kernel 上，与 dense 的唯一区别是跳过了哪些块。
- 以 HF SDPA 为基线会把加速夸大约 2 倍，所以我们不用它当主基线。
- 执行底座对所有方法相同：分段 CUDA graph（vLLM 式）、FA4 prefill、FA4 canvas 追加。
- 修掉了官方实现的一个低效之处：每步都把整个 encoder KV 重新拼接一遍。修复后生成的 token 逐位不变，所有方法的 64K 请求都快 5–6%。这一步只让基线更强，不算我们的贡献。

**【Speaker notes】**
- **kernel 基准：** `scripts/v27_kernel_bench.py`，结果在 `kernel_bench/kernel_bench.jsonl`。
  - 环境：mpk H100 80GB，torch 2.12.1+cu130，FA4 为 vLLM flash-attn cute 构建。
  - 形状：一层 GLOBAL 调用，16 个 query head × 256 个 canvas query，2 个 KV head，head_dim 512，bf16；key 数 = 上下文 + 256；双向无 mask。
  - 计时：CUDA events，10 次预热，取 50 次的中位数。
  - 每个长度都核对了全保留输出与 FA4 dense 逐位一致。
- **端到端 D_native 数字：**
  - LB 32K/64K 来自 v3 面板（`fa4_panel_v3/`，旧底座 piecewise_v1，每区间 24 格）；
  - LB 标准池与 AIME 来自 q1v3 面板（`quality_panel_q1v3/`，piecewise_v2）。
- **FA4 dense 与全保留：** v3 面板中 FA4 dense 的请求时间是全保留的 1.011–1.012×，解码时间 1.013–1.021×，生成的 token 相同。
- **FlashInfer：** 早先在同一进程里的测试中，它在 head_dim 512 下与 FA4 持平（`official_baseline/`）。FA2/FA3 不支持 head_dim 512。
- **底座：**
  - piecewise_v2：decoder 用 `torch.compile(mode='reduce-overhead')` 分段编译，GLOBAL 注意力模块留在图外逐算子执行，LOCAL 注意力在图内；prompt prefill 与 GLOBAL canvas 追加用 FA4 causal；采样器按官方方式编译。
  - piecewise_v3：v2 的基础上，GLOBAL decoder 注意力改用常驻 [prefix | canvas] KV 缓冲区，每个 canvas 拷贝一次 prefix，每步只写 256 行，不再每次 torch.cat；另外对 batch 1 去掉一次 `finished.any()` 主机同步。
  - 验证：LB 32K/64K、3 个方法各重复 2 次，tokens_sha 与 v2 完全一致；显存峰值同为 70.87 GiB；32K 编译后 forward 从 34.29 降到 32.02 ms（`substrate/`）。

**【要点】**
- **64K 上有稳定的端到端加速：** 请求约快 13–14%，去掉 prefill 后解码约快 21%，精度不降（M3 R6 DP −ln2 答对 23 vs 18，+5/−0）。
- **速度复现了五次：** 阈值扫描（v2 底座）0.868、变体面板（v3）0.872、最终面板（v3）0.869、SparseD 对比面板 0.865、新机器 dlm2 上的 M2 面板 0.821。前四个在同一批机器上生成的 token 完全相同，所以答对数也相同（23 对 18），这不是精度的独立复现；dlm2 上 token 不同，答对是 18 对 21，在噪声内。
- **32K 没有显著加速：** 最好 0.90×，置信区间跨过 1。
- **标准池（10–19K）上不带门限的稀疏方法比 dense 慢。** 加 32K 长度门限后，短上下文走 dense，精度与 dense 完全一致，开销约 0.5%，长上下文的收益全部保留。这是可部署的配置。
- **Fan 原版 M1/M2/M3 在 LongBench 各档都比 dense 慢（1.12–1.49×；M3 在 32K 和 64K 上置信区间刚好跨过 1）：** 每步选块和每 8 步重新观测的开销，超过了省下的注意力（见实验 5）。

**【Speaker notes】**
- **协议：** `v27_final_lb_f1_79c81baf9ac23611`（`specs/v27_final_lb_f1.json`），生成前冻结。
- **题目与 seed：**
  - LongBench-v2 标准池 12 题（10.5–19.3K tokens，4 类任务）；
  - LB-long 32K 档与 64K 档各 12 道正式题（每档 24 题中另外 12 道是开发题，不参与评分）；
  - seed 101/202/303，only-first（每格只取第一次输出）。
- **机器：** 2 块 H100（dllm 与 mpk），同一格的 8 个方法在同一台机器上跑；底座 piecewise_v3；每个方法计时前先做两个 prompt 的预热。
- **评分：** v15 LongBench 评分器，四选一，gold 按 sha 固定。
- **方法定义：**
  - dense：FA4 block-sparse API，全部块保留。
  - Fan M1（R1 A8）：块选择用"历史 QK + 当前投影 V（rank-32）+ 当前参考范数 + query 敏感度 T"估计跳过每个块的输出风险，每步决策，每 8 步重算一次完整 QK。
  - Fan M2c：同 M1，但 V 用块内均值（compact pooled）。
  - Fan M3（R3）：每 3 步做一次 M1 决策，中间沿用。
  - 所有方法的注意力输出都用当前 QK 和原始 V，选块只决定跳过哪些块。
  - B：A64 融合观测（每个 canvas 第 1 步 dense、第 2 步 dense 并同时算选块统计），之后整个 canvas 沿用这张 map；阈值为默认 log 阈值 −3.18。
  - M3 R6 DP −ln2：A64 融合观测；风险相对 dense prefix 状态计算（DP，可并行，0.27 ms/层）；每 6 步决策一次；log 阈值 −3.874。
  - 32K 门限：key 数 < 32768 时整层走 dense（与 dense 基线同一个 FA4 全保留路径）。
  - 所有稀疏方法都只作用于 5 个 GLOBAL 层（5/11/17/23/29），25 个 LOCAL 层（窗口 1024）保持 dense；选块都走异步侧流。
- **prefill：** 所有方法的 prefill 比值 P = 0.96–1.08，说明我们没有改变 prefill。
- **每 canvas 步数：** 64K 上 B 为 1.044（多 4%），M3 R6 DP −ln2 为 0.952（少 5%）。
- **数据：** `final_panel_f1/`（README、summary_lb、cells_lb；剔除异常配对的敏感性表 `summary_lb_sensitivity.csv`）。

## 实验 3：阈值扫描：端到端最优阈值在哪里

> "越稀疏，去噪步数越多"组里已经知道：同学 9/23 的 PPT 里，value_aware 在 30% 稀疏度下 97 步，dense 88 步。这一页只讲新的信息：端到端最优点在哪里。

**【正文顶部】** LB-v2 32K/64K 正式题 × 3 seed（36 格/方法/档）· M3 R6 DP 五档阈值（+ln2 … −3ln2），B 与 M1 DP 各两档 · FA4 + piecewise_v2

**【主结果】（64K，dense 答对 18/36）**

| 阈值移位 | 请求 W [95% CI] | 解码 S | 步数/canvas [95% CI] | 每次调用 S/N | 答对 |
|---|---|---:|---|---:|---:|
| +ln2（更稀疏） | 1.074 [0.915, 1.255] | 1.091 | **1.395 [1.232, 1.573]** | **0.774** | 20 |
| 0（默认） | 0.970 [0.855, 1.086] | 0.939 | 1.101 [1.038, 1.166] | 0.810 | 19 |
| **−ln2** | **0.868 [0.807, 0.932]** | **0.795** | 0.952 [0.918, 0.991] | 0.846 | **23** |
| −2ln2 | 0.875 [0.773, 0.970] | 0.816 | 0.960 [0.910, 1.006] | 0.877 | 20 |
| −3ln2（保留最多） | 0.958 [0.857, 1.055] | 0.941 | 1.001 [0.957, 1.047] | 0.918 | 22 |

**32K（dense 答对 28）：**

| 阈值移位 | 请求 W | 步数/canvas | 答对 |
|---|---:|---:|---:|
| +ln2 | 1.236 | 1.363 | 23 |
| 0 | 1.003 | 1.072 | 24 |
| −ln2 | 0.951 | 0.996 | 31 |
| −2ln2 | 0.926 | 0.976 | 27 |
| −3ln2 | 1.008 | 0.985 | 27 |

**【要点】**
- **端到端最优点是 −ln2（64K 为 0.868×，精度也最好），不是最稀疏的那一档。**
- 最稀疏的 +ln2 每个 canvas 多 36–40% 的步数，吃掉了单次调用的节省；步数随稀疏度增加这一点是已知现象。
- **B 在默认阈值下同样快（0.866 [0.823, 0.913]），且只多 4% 的步数；** 给 B 多保留块（−2ln2）反而变慢（0.941）。
- **32K 上默认阈值和 +ln2 有掉分迹象**（24、23 vs 28），多保留块后恢复（−ln2 为 31）。

**【Speaker notes】**
- **协议：** `v27_long_lb_sweep_s1_322b24218397083a`（`specs/v27_long_lb_sweep_s1.json`），生成前冻结。
  - 题目：与实验 2 相同的 12+12 道正式题，seed 101/202/303，底座 piecewise_v2，2×H100，同一格同一台机器。
  - 方法：dense、Fan M3 R3 A8、M3 R6 DP 五档阈值移位、B 两档（0、−2ln2）、M1 R1 DP 两档（0、−2ln2），共 11 个。
- **阈值移位的含义：** 加在选择器的对数风险阈值上，正数跳过更多块，负数保留更多。
- **S/N** 是摊销的每次调用成本，不是单次 forward 的直接价格；直接计时见实验 5。
- **其他结果：**
  - M1 R1 DP 在 32K 掉分：21 vs 28（+4/−11，p = 0.12），步数 +10%。
  - Fan M3 R3 A8 在两档都是 1.11–1.15×，步数不变，它的开销来自观测和选块，不来自步数。
- **数据：** `threshold_sweep_s1/README.md`，含完整两档表格与 cells.csv。

## 实验 4：短上下文精度（AIME26、LongBench 标准池）与长度门限

**【正文顶部】** AIME26 全部 30 题 · 最终面板 × 4 seed = 120 格，8 个方法（新底座）· 早先 q1v3 面板 × 2 seed = 60 格，11 个方法 · 前缀 ≤ 约 9K keys

**【主结果】（q1v3，60 格，dense 答对 35）**

| 方法 | 答对 | +/− vs dense | 符号检验 p | 请求 W [95% CI] |
|---|---:|---|---:|---|
| HF SDPA（精确 dense，噪声参照） | 36 | +7/−6 | 1.00 | 1.01 [0.87, 1.13] |
| Fan M1 / M2c / M3（A8） | 29 / 33 / 31 | +4/−10、+5/−7、+2/−6 | 0.18 / 0.77 / 0.29 | 1.09 / 1.06 / 1.06 |
| B | **26** | +4/−13 | **0.049** | 1.07 [0.91, 1.24] |
| M3 R6 rp / M1 DP / M3 R6 DP | 30 / 33 / 31 | +4/−9、+4/−6、+8/−12 | 0.27 / 0.75 / 0.50 | 1.01 / 1.01 / 0.99 |
| M3 R6 DP −2ln2（多保留） | 27 | +5/−13 | 0.10 | 0.98 |
| **M3 R6 DP + 8K 长度门限** | **35** | **+0/−0** | 1.00 | 0.95 [0.83, 1.02] |

**【要点】**
- **短上下文没有加速可拿：** 所有稀疏方法的请求时间都在 0.98–1.09，置信区间跨过 1（这个面板有 8 条请求在计时中捕获了新图，没有剔除；速度以下面的最终面板为准）。原因是 AIME 前缀短，GLOBAL 注意力占比很小，证据链见实验 9。
- **不带门限的稀疏方法全部净减分，其中只有 B 显著（26 vs 35，p = 0.049）。** 精确 dense kernel 替换本身就会让 13/60 格结果翻转，所以单个方法的差异多在噪声内，但方向一致。
- **长度门限让短上下文走 dense，精度与 dense 完全一致。** 部署配置：短上下文 dense，长上下文稀疏。
- **与组里的观察一致：** 同学的 PPT（9/30）里，AIME 90 格上 dense 44/90，value_aware 37/90，regroup+value_aware 42/90，结论是 AIME 上实际可承受的稀疏度约 40–50%。
- **最终面板（AIME 120 格，4 seed，新底座）已出：**

| 方法 | 答对（120 格） | +/− vs dense | 请求 W [95% CI]（剔除计时中捕获新图的配对） | sec/task（同样剔除） |
|---|---:|---|---|---:|
| dense（FA4） | 65 | | 1 | 14.02 |

## 实验 5：三层加速：kernel → 注意力模块 → 端到端（论文式口径）

**【正文顶部】** 同一个 FA4 kernel · 真实 GLOBAL 层形状 · 模块级在真实请求中计时（含每 canvas 的 dense 首步、观测与决策）· 64K 档

## 实验 7：新颖性检查与 SparseD 正面对比

**【正文顶部】** 2025–2026 年扩散语言模型稀疏注意力相关工作 · SparseD 移植到同一 FA4 kernel 与底座 · LB 32K/64K × 3 seed · 504 次运行

**【主结果：已有工作】**

| 工作 | 做法 | 与我们的关系 |
|---|---|---|
| SparseD（ICLR 2026，arXiv 2509.24014） | 前 20% 的步用完整注意力；之后按块平均注意力分数一次性选出模式（长上下文保留 30%，块 128）并一直复用；FlexAttention；LLaDA-1.5 / Dream-7B；固定 32–1024 步；64K、1024 步时比 FlashAttention 快 1.50× | ≈ 我们的 B |
| PulseCol（arXiv 2605.20813） | 列稀疏，在少数中间步刷新模式；比 FlashAttention 最多快 1.95× | ≈ M3 的定期刷新 |
| FlashBlock（arXiv 2602.05305） | 块扩散中跨步复用块外 KV 的注意力输出与 log-normalizer，块内更新少于 2 个 token 才复用；块大小 4–8；吞吐最多 1.44× | 我们的 canvas 有 256 个 token，每步都被重新加噪，复用条件几乎不会触发 |
| BA-Att（arXiv 2605.19726） | 块近似稀疏注意力，用范数排序加 QK 方差修正选块 | 选块不看 V |

**【要点】**
- **B 的"观测一次、复用整个 canvas"与 SparseD 撞车。** M3 的定期刷新也有相近工作。
- **原先认为可能的新意，以及今天数据给出的现状：**
  1. Fan 的选块会看 V：用 QK 加投影 V 估计"跳过这个块会让输出变多少"，SparseD 只看注意力分数。**现状：没有得到数据支持**：LongBench 64K 上速度与 SparseD 最好的一档无显著差别，精度都在噪声内；AIME 实际稀疏度 66% 时我们的选块显著掉分，SparseD 没有（实验 9）。

  3. 基线更严格（FA4 而不是 FlashAttention/Flex），并且三层加速都报。**现状：这是评测上的严格性，不是方法贡献。**

**【Speaker notes】**
- **协议：** `v27_long_lb_m2_c1`（`specs/v27_long_lb_m2_c1.json`），生成前冻结；只在 dlm2 上跑，4 个方法的每一格都在同一块 GPU 上。
- **M2c R6 DP −ln2 的定义：** 均值 V 用 Fan M2c 的 pooled-compact 近似，其余同 M3 R6 DP −ln2（每 6 步决策一次、每个 canvas 一次融合观测、dense-prefix 风险、选块放在副 stream、阈值 −ln2）。
- **收据核对，全部通过：**
  - M2c R6 的 mu_mode 为 pooled_compact，M3 R6 为 exact（投影 V）；
  - M2c R6 的 pooled 均值构建次数等于 DP 选块次数，M3 R6 为 0；
  - 两者的决策间隔都是 6，风险状态都是 dense-prefix，观测和预热结构相同；
  - 计时期间没有一条请求捕获新图。
- **跨机器可复现性：** 跨机器的生成不能逐位复现：同一题、同一 seed、同一方法，dlm2 上的 token 与 dllm/mpk 上都不同（dense 也是）。三台都是 H100 80GB HBM3，驱动小版本和软件环境略有差别。同一台机器上重跑则完全一致：之前三个 64K 面板的精度都是 23 对 18。所有配对都在同一台机器内比较，所以速度比与精度差本身是公平的；但不同机器之间，同一方法的答对数会相差约 ±3/36，这是精度对比的噪声下限。64K 上 M3 R6 DP −ln2 在 dllm/mpk 上是 23 对 18，在 dlm2 上是 18 对 21，合计 41 对 39，看不到一致的精度差。

## 实验 9：AIME 固定稀疏度：我们的选块 vs SparseD（与同学同口径）

**【正文顶部】** AIME26 全部 30 题 × 3 seed = 90 格 · 目标稀疏度 30/40/50%（只作用于 GLOBAL 层的 prefix 块）· 我们：按 M1-DP 风险取 top-k · SparseD 移植：前 1 步 dense 后沿用 · FA4 + piecewise_v3

**【主结果】（dense FA4 = 1）**

| 方法（目标稀疏度） | 实际稀疏度 | 答对（90 格，dense 49） | +/− | 请求 W [95% CI] | 步数 N [95% CI] | 输出长度 T | 每步成本 S/N [95% CI] |
|---|---:|---|---|---|---|---:|---|
| 我们 topk 30% | 24% | 49 | +9/−9 | 1.076 [1.028, 1.135] | 1.087 [1.019, 1.171] | 1.045 | 0.990 [0.963, 1.018] |
| 我们 topk 40% | 32% | 48 | +7/−8 | 1.086 [1.040, 1.133] | 1.106 [1.033, 1.179] | 1.047 | 0.985 [0.957, 1.017] |
| 我们 topk 50% | 41% | 48 | +9/−10 | 1.062 [1.001, 1.128] | 1.078 [0.977, 1.191] | 1.047 | 0.988 [0.943, 1.033] |
| SparseD 30% | 23% | 48 | +6/−7 | 0.988 [0.952, 1.029] | 0.978 [0.920, 1.040] | 0.993 | 1.011 [0.984, 1.040] |
| SparseD 40% | 32% | 47 | +8/−10 | 1.034 [0.990, 1.080] | 1.045 [0.971, 1.121] | 1.039 | 0.990 [0.955, 1.025] |
| SparseD 50% | 40% | 47 | +7/−9 | 1.021 [0.983, 1.063] | 1.025 [0.964, 1.096] | 1.018 | 0.998 [0.967, 1.027] |

**【要点】**
- **精度：两种选块在 24–41% 的实际稀疏度下都不掉分**（47–49 对 49），差异都在噪声内。与同学"AIME 上可承受 40–50% 稀疏度"的结论一致。
- **速度：没有任何一档变快。** 每步成本只下降 0–1.5%（不显著），因为 AIME 上下文最多约 8.4K key，GLOBAL 注意力只占一步约 5–6%（8K key 时的估计，见备注里的证据链）。
- **我们的选块在 AIME 上反而慢 6–9%：** 原因不是每步更贵，而是去噪步数多了 8–11%、输出长了约 5%。SparseD 的步数基本不变。
- **结论：** 在 FA4 基线上，AIME 没有注意力稀疏的加速空间；能说的是"同等稀疏度下精度不降"。同学 PPT 里的 AIME 提升（约 6%，同时少对 7/90）是在他们自己的执行栈上测的（JAX/FA3，生成上限 2048 token），dense 用哪种注意力 kernel PPT 没写，两边的加速不能直接比较，需要向同学确认。
- **70/80% 目标稀疏度（实际 56–66%）：** 两种选块都掉分、都变慢；66% 时我们的选块显著掉分（23 对 34），SparseD 仍是 29。高稀疏度区我们不如 SparseD（负结果，详见备注）。

**【Speaker notes】**
- **为什么 AIME 在 FA4 基线上没有提升空间（证据链，前三条是实测）：**
  1. AIME 提示约 80–380 token，生成最多 8192 token，GLOBAL 注意力的 key 数最多约 8.4K，多数步在 2–6K。
  2. kernel（`kernel_bench/README.md`）：8K key 时 FA4 dense 一次 GLOBAL 调用 0.44 ms；保留 50% / 30% / 10% 只快 1.7 / 2.3 / 3.3 倍（64K 时 2.0 / 3.2 / 7.3 倍）。5 层合计 dense 约 2.2 ms。
  3. 模型内整步（`substrate/README.md` 第 3 节）：CUDA graph 底座上用真实状态重放一次 forward，块选择直接给定、不计选块开销；17K key（AIME 最长上下文的 2 倍）时 dense 40.7 ms，保留 50% / 30% / 10% 是 0.94 / 0.93 / 0.91 倍。AIME 的 key 更少，能省的只会更少。
  4. 估计：8K key 时 GLOBAL 注意力约占一步 5–6%，保留 50% 时每步最多省约 2–3%。
  5. 本页实测：每步成本 0.95–1.01，而步数随稀疏度增加 8–27%，没有一档变快。
  6. 对照：64K 上同样的方法每步便宜约 16%，GLOBAL 注意力约占 dense 请求 14%，才能转成约 13% 的请求加速。
  7. 我们上周在 FIXED16 面板上测到 AIME 生成 1.10–1.22×，那次基线是 HF 原生 eager 路径（SDPA、没有 CUDA graph）且包含 LOCAL 跳块；换成 FA4 + CUDA graph 后消失。这说明 AIME 上的加速取决于基线。
- **实际稀疏度** 按构造计算：canvas 自己的 4 个 key 块总是保留，每个 canvas 的第一步是 dense，其余步在 prefix 块上跳过目标比例。两种选块的实际稀疏度对齐（24/32/41% 对 23/32/40%），所以是同等稀疏度下的对比。面板只记最少的遥测，这不是逐块统计。
- **topk 是我们加的变体：** Fan 的原版和阈值版都没有"目标稀疏度"旋钮；阈值版 M3 R6 DP −ln2 在 AIME 上的稀疏度只有 2–12%（附录 A）。为了与 SparseD 和同学在同一稀疏度下比较，用 M1-DP 风险排序取 top-k，其余设置同 M3 R6 DP。
- **收据核对，全部通过：** topk 各档每 6 步做一次 DP 选块、每次选块都生成 FA4 块表、每个 canvas 第一步是 dense；SparseD 每个 canvas 每层观测一次，其余步沿用。每个方法最多 2 条请求在计时中捕获了新图，速度比已剔除这些配对。
- **协议：** `v27_aime_sparsity_t1`（`specs/v27_aime_sparsity_t1.json`），30 题 × seed 101/202/303，两台机器，每格 7 个方法在同一台机器上，生成前冻结。汇总表由 `aime_sparsity_panel_t1/table.md` 生成。

## 实验 10：更长的上下文：96K 与 128K

**【正文顶部】** LB-v2 自然长度 84–104K（12 题）与 112–144K（12 题）· seed 101/202 · 6 个方法（dense、Fan 原版 M1/M2c/M3、B、M3 R6 DP −ln2）· FA4 + piecewise_v3 · 单卡 H100 80GB

**【主结果】**

**128K 放不下：** 所有方法（dense FA4 也一样）在 128K 的单次预填充里 OOM（已分配 76.7 GiB 时再申请 1.38 GiB 失败），第一格之后就停了。

**96K 只能放下一半：** 84–104K 的 12 道题里，提示不超过 95,074 token 的 6 道所有方法都能跑，达到 98,282 token 以上的 6 道连 dense 都在预填充时 OOM。所以这个模型在单卡 H100 80GB 上的 dense 上限在 95K 到 98K token 之间；更长的上下文要用分块预填充或多卡，这对 dense 和稀疏都一样。

**能跑的 12 格**（6 道题 × seed 101/202，mpk 与 dlm2，每格 6 个方法在同一台机器上）：

| 方法 | 请求 W [95% CI]（剔除异常配对） | 每步成本 S/N [95% CI] | 步数 N [95% CI] | 答对（12 格，dense 5） |
|---|---|---|---|---:|
| **我们 M3 R6 DP −ln2** | 0.948 [0.863, 1.024] | **0.818 [0.715, 0.981]** | 1.184 [0.996, 1.405] | 6 |
| B | 1.042 [0.927, 1.179] | 0.839 [0.699, 1.082] | 1.375 [1.040, 1.886] | 6 |

- **但步数多了 18%，请求级不显著（0.948）。** 只有 12 格，步数的随机变化很大（同一格两个方法的步数可以差 3 倍），这个点只作参考。
- **端到端最优仍然在 64K 这一档：** 32K 不显著，64K 快约 13%，96K 每步更省但格子太少、步数波动大；128K 在单卡上跑不了。
