## 1. 一句话总结

- **长上下文（64K 档，56–76K tokens）：** 在最快的官方 dense 基线（FlashAttention-4）上，**每步解码成本稳定降低 17–19%**（所有面板与留出新题一致），精度不降。**请求级加速不稳：** 挑阈值用的 12 道正式题上 M3 R6 DP −ln2 快约 13%（0.869），但 12 道留出新题上不快（1.026），因为稀疏版输出平均长了 18%；合并 24 题为 0.944 [0.887, 1.004]（不显著），B 为 0.923 [0.874, 0.980]（约快 8%）。详见更新 6。
- **短上下文（AIME、10–19K 的 LongBench）：** 没有加速。AIME 120 格上，我们选定的 M3 R6 DP −ln2 精度与 dense 完全持平（65 vs 65），只有 B 有下降趋势。加长度门限（短上下文直接走 dense）后，精度与 dense 逐格一致。
- **Fan 原版 M1/M2/M3：** 长上下文上都显著比 dense 慢（1.12–1.57 倍），原因是选块本身的开销超过了省下的注意力；AIME 上 M1 显著更慢，M2c/M3 与 dense 无显著差别。
- **新颖性：** 最接近的已有工作是 SparseD（ICLR 2026），与我们的 B 撞车。移植到同一 FA4 kernel 的正面对比显示，速度上我们与 SparseD 最好的一档没有显著差别（64K 0.957 [0.872, 1.072]），按撞车处理；LongBench 上精度都在噪声内（更新 3），AIME 高稀疏度下我们的选块反而更差（更新 5）。目前没有数据支持"看 V 的选块优于只看注意力分数的选块"。
- **AIME：** 同等稀疏度（实际 24–41%）下我们的选块和 SparseD 都不掉分，但在 FA4 基线上都没有提速，原因见 5.6（更新 2）。实际稀疏度到 66% 时我们的选块显著掉分（23 对 34），SparseD 仍是 29：高稀疏度区我们不如 SparseD（更新 5）。

## 2. 背景：我们在加速什么

**模型与解码方式**
- 模型：DiffusionGemma-26B-A4B（MoE，激活参数约 4B）。
- 解码方式：以 256 个 token 为一个 canvas 块，块内反复去噪。每个 canvas 的去噪步数由模型自带的置信度停止规则决定（置信度阈值 0.005、stability 1、最多 48 步），这就是"原生自适应停止"。一个 canvas 完成后追加到上下文，再生成下一个。
- 生成设置：thinking 模式开启，每个请求最多生成 8192 个 token（32 个 canvas），遇到 EOS 停止。

**注意力结构**
- 30 层 decoder 里，5 层是 GLOBAL 注意力（第 5/11/17/23/29 层）：看全部上下文，head_dim 512，16 个 query head、2 个 KV head。
- 其余 25 层是 LOCAL 注意力：滑动窗口只看最近 1024 个 key。
- 长上下文里真正随上下文变贵的只有 5 层 GLOBAL，所以**我们只稀疏化 GLOBAL 层**，LOCAL 层一直保持 dense。

**"稀疏"在这里具体是什么**
- 每次 GLOBAL 注意力调用里，query 是 canvas 的 256 个位置，key 是整个上下文。把 key 按 64 个一组切成块（tile），query 按 128 个一组，稀疏注意力就是跳过一部分 (query 块, key 块) 组合。
- 本文的"保留比例"指保留下来的上下文 key 块占多少，"稀疏度" = 1 − 保留比例。
- canvas 自己的 key 块总是保留。每个 canvas 的第一步总是 dense。

## 3. 方法名词表：M3 R6 DP −ln2 这些都是什么意思

**Fan 的三个方法（组里的核心方法，每次比较都必须包含）**
- **M1：** 选块时估计"跳过这个块，注意力输出会变多少"。用到的信息有：
  - 历史上观测到的 QK 分数（每隔几步观测一次，不是每步都算）；
  - 当前的 V 投影到 32 维后的值；
  - 当前参考范数和 query 敏感度 T。

  风险低于阈值的块就跳过。输出始终用当前的 QK 和原始 V 精确计算，选块只决定跳过哪些块。
- **M2：** 同 M1，但 V 用块内均值代替投影 V（本周跑的是 M2c，即 compact pooled 版本）。
- **M3：** 同 M1，但不是每步都重新决策，而是每 R 步决策一次，中间沿用上一次的块选择。

**参数与变体后缀**

| 写法 | 含义 |
|---|---|
| R1 / R3 / R6 / R12 | 每 1 / 3 / 6 / 12 步做一次选块决策（M1 = R1） |
| A8 / A64 | 每 8 步 / 每个 canvas 一次，重新观测一次 QK 分数。A64 的实际效果是每个 canvas 只观测一次，而且观测与该 canvas 第二步的 dense 计算融合在同一个 kernel 里（fused observation） |
| DP（dense-prefix） | 风险相对"所有更早的块都保留"的状态来算，而不是相对"已保留的块"。这样所有块可以并行判断，一次决策从约 2–8 ms/层降到 0.27 ms/层 |
| −ln2 / −2ln2 / +ln2 | 阈值移位：加在对数风险阈值上。负数保留更多块（更保守），正数跳过更多。默认阈值是 −3.18，−ln2 后是 −3.874 |
| B | "观测一次后固定"：每个 canvas 第一步 dense，第二步观测并选块，之后整个 canvas 都用这张块选择，不再更新（hold-only） |
| async / rp | 选块计算放到另一条 CUDA 流上异步执行 / 流水线化；不改变决策，只省时间 |
| gate32k | 长度门限：上下文 key 数少于 32768 时整层直接走 dense |
| Fan 原版 | 即 M1 R1 A8、M2c R1 A8、M3 R3 A8，也就是按原始定义不加任何工程优化的版本 |

| topk XX%（固定稀疏度变体，本周新加） | 用 M1-DP 风险给 prefix 块排序，每个（head, query 块）只保留风险最高的 (1 − XX%) 的块；其余同 M3 R6 DP（每 6 步决策一次、A64 融合观测、副流选块）。Fan 的原版和阈值版都没有"目标稀疏度"这个旋钮，这是我们为了和 SparseD、同学在同一稀疏度下比较而加的 |
| SparseD kXX sY（移植） | SparseD（ICLR 2026）移植到同一 FA4 kernel：每个 canvas 前 Y 步 dense，第 Y 步用平均池化的注意力分数给块排序，保留 XX% 的 prefix 块，之后沿用到 canvas 结束。k10/k20/k30 = 保留 10/20/30%；s1 = 前 1 步 dense，s10 = 前 10 步 dense（论文默认的"前 20% 步"按 48 步上限折算）。AIME 面板里写作 SparseD sXX，XX 是目标稀疏度（s30 = 保留 70%） |
| D_fa4_allkept / dense | dense 基线：FA4 block-sparse 接口保留全部块，与 FA4 dense 逐位一致 |

所以 **"M3 R6 DP −ln2"** 读作：
- M3，每 6 步决策一次；
- 每个 canvas 融合观测一次（A64）；
- 用 dense-prefix 方式并行算风险；
- 阈值比默认保守 ln2（多保留一些块）。

**典型保留比例（稀疏度）**
- 取自保真度诊断，是开发题上的中位数，只统计固定 map 期间的 GLOBAL 调用：

  | 方法 | 64K 保留（稀疏度） | 32K 保留（稀疏度） |
  |---|---:|---:|
  | B | 10%（约 90%） | 15%（约 85%） |
  | M3 R6 DP，默认阈值 | 7%（约 93%） | 12%（约 88%） |
  | M3 R6 DP，−ln2 | 12%（约 88%） | 21%（约 79%） |
  | Fan 原版 M1 | 15%（约 85%） | 22%（约 78%） |

- AIME 前缀短，稀疏度只有 2–12%。
- 整体注意力的实际稀疏度更低：每个 canvas 的前两步是 dense，25 层 LOCAL 始终 dense。

## 4. 实验设置：怎么保证对比公平

**Dense 基线**
- 用官方 FlashAttention-4（vLLM 的 flash-attn cute 构建）的 block-sparse 接口，把所有块都保留，结果与 FA4 dense 逐位一致，而且快 1–2%。
- 所有稀疏方法跑的是同一个 FA4 kernel，与 dense 的区别只在跳过了哪些块。
- HF 模型的默认路径（head_dim > 256 时先把 K/V 复制 8 份，再走 PyTorch SDPA 的内存高效后端）在 64K 上 kernel 慢约 2.1 倍（6.16 对 2.91 ms，`official_baseline/README.md`），端到端慢 1.6–2.2 倍，所以不用它当基线，否则加速会被夸大。（更正：此前写的"kernel 慢 5.8–7.5 倍"是用 `enable_gqa` 调 SDPA 测的，走的是 math 后端，不是 HF 的实际路径。）

**执行底座：所有方法相同**
- decoder 用分段 CUDA graph 编译（vLLM 的做法），prompt prefill 用 FA4。
- 还修掉了官方实现的一个低效之处：每一步都把整个 KV 缓存重新拼接一遍。修复后生成的 token 逐位不变，所有方法都快 5–6%。

**流程**
- 每个面板在生成前冻结协议（题目、seed、方法、机器分配）。
- 同一格（题目 × seed）的所有方法在同一块 GPU 上跑，比较都在同一台机器内配对。本周共用 3 块 H100 80GB（dllm、mpk、dlm2；dlm2 是 9/30 新加的机器）。
- 跨机器的生成不能逐位复现（驱动小版本和软件环境略有差别），同一方法在不同机器上的答对数会差约 ±3/36；同一台机器上重跑则完全一致。

**统计**
- 每格（题目 × seed）只取第一次输出。
- 速度用与 dense 配对后的几何平均比值，95% 置信区间按题目聚类 bootstrap。
- 精度报告答对格数和"+只有该方法对 / −只有 dense 对"，用符号检验。
- 计时时如果某次请求在计时期间捕获了新的 CUDA graph（首次遇到新形状），它的时间会多出几秒到几十秒。从 9/30 起，速度比同时报告剔除这类配对后的值（Wc）；LongBench 各面板没有这类请求，AIME 面板每个方法 1–4 条。

**缩写与口径**

| 缩写 | 含义 |
|---|---|
| 格 | 一个（题目, seed）组合；每格每个方法只取第一次输出 |
| W | 请求墙钟时间比（方法 / dense），含 prefill；< 1 表示更快 |
| Wc | 同 W，但剔除计时中捕获新 CUDA graph 的配对 |
| S | 去掉 prompt prefill 后的解码时间比（GPU 时间线） |
| P | prefill 时间比；所有方法都约等于 1，说明没有改动 prefill |
| N | 去噪步数（decoder 调用次数）比 |
| N/C | 每个 canvas 的平均步数比 |
| T | 输出 token 数比 |
| S/N | 每步平均解码时间比，是摊销值（包含采样等每步开销），不是单次 forward 的直接计时 |
| sec/task | 每格请求时间的算术平均（组里 PPT 的口径） |
| 答对 x（dense y） | strict correct 的格数 |
| +a/−b | 只有该方法答对 / 只有 dense 答对的格数；p 值是配对符号检验（双侧） |
| [lo, hi] | 按题目聚类 bootstrap 的 95% 置信区间；跨过 1 表示不显著 |
| 实际稀疏度 | 固定稀疏度面板里按构造算的、被跳过的 GLOBAL key 块占全部 GLOBAL 调用的比例（canvas 块总保留、每个 canvas 第一步 dense），不是逐块遥测 |
| 底座 piecewise_v2 / v3 | decoder 分段 CUDA graph + FA4 prefill；v3 另外去掉每步 KV 拼接，生成的 token 与 v2 相同 |
| FA4 | FlashAttention-4（vLLM 的 flash-attn cute 构建），dense 和稀疏用同一个 kernel |

**数据集**

| 数据 | 来源 | 长度 | 题数 | 每个方法的格数 |
|---|---|---|---:|---|
| LongBench-v2 标准池 | 官方题 | 10–19K tokens | 12 | 3 seed = 36 格 |
| LongBench-v2 32K 档 | 官方题，按自然长度分档，不截断 | 28–40K tokens | 12 道正式题（另 12 道开发题不评分） | 3 seed = 36 格 |
| LongBench-v2 64K 档 | 同上 | 56–76K tokens | 12 道正式题（另 12 道开发题不评分） | 3 seed = 36 格 |
| LongBench-v2 96K 档（9/30 新加） | 同上 | 84–104K tokens（只有 ≤ 95K 的 6 道能在单卡上跑） | 12 | 2 seed = 24 格，可跑 12 格 |
| LongBench-v2 128K 档（9/30 新加） | 同上 | 112–144K tokens | 12 | 单卡放不下，未产出结果 |

- seed 为 101/202/303（AIME 最终面板加 404）。

配对比值（相对 dense，几何平均，95% CI）：
- **64K：**
  - M3 R6 DP −ln2：请求 0.869 [0.805, 0.933]，解码 0.783；
  - B：请求 0.864 [0.825, 0.905]，解码 0.788；
  - M3 答对 +5/−0（p = 0.06，不宣称提升，只说不降）。
- **32K：** M3 R6 DP −ln2 请求 0.902 [0.780, 1.015]，B 0.935 [0.862, 1.016]，都不显著。
- **标准池：** 不加门限时比 dense 慢（1.04–1.08）。加 32K 门限后与 dense 完全一致（同样的 token，+0/−0，额外开销约 0.5%）。
- **Fan 原版：** 64K 1.12–1.49×，32K 1.15–1.33×，标准池 1.17–1.30×，都比 dense 慢。

**复现情况：** M3 R6 DP −ln2 在 64K 上的请求时间，三次分别是：
- 阈值扫描 0.868（旧底座）；
- 变体面板 0.872（新底座）；
- 最终面板 0.869（新底座）。

三次的答对数完全相同。原因是新旧底座、同一批机器生成的 token 完全一样，所以这是速度的复现，不是精度的独立复现。

之后又有两次速度复现：SparseD 对比面板 0.865（同一批机器，精度同样是 23 对 18）；M2 面板在新机器 dlm2 上 0.821（token 不同，精度 18 对 21，在噪声内）。

### 5.3 AIME（短上下文推理）

**早先面板（60 格，2 seed，dense 答对 35）**
- 不加门限的稀疏方法全部净减分，只有 B 显著（26，p = 0.049）；其余 27–33，单个都不显著。
- 精确 dense kernel 替换本身就会让 13/60 格的结果翻转，所以单个差异大多在噪声内，但方向一致。
- 8K 门限版在 AIME 上走 dense，答对 35，与 dense 完全一致。
- 速度：AIME 前缀不超过约 9K key，稀疏在这里本来就没有加速空间（请求时间 0.98–1.09，都不显著；这个面板有 8 条请求在计时中捕获了新图、没有剔除，速度以最终面板为准）。
- 这与同学在 AIME 上的观察一致：实际可承受的稀疏度只有 40–50%。
- 出处：`quality_panel_q1v3/README.md`。

- **B 是唯一下降的：** 58/120，120 格下已不显著；早先 60 格面板里是 26 vs 35，显著。
- **速度：** AIME 上我们的方法与 dense 持平（1.008），Fan 原版 M1 显著更慢，其余在噪声内。原因见 5.6。
- 出处：`final_panel_f1/README.md`。

### 5.4 加速在三层上怎么缩小（64K，论文口径）

| 层级 | B | M3 R6 DP −ln2 | Fan 原版 M1 / M2c / M3 |
|---|---:|---:|---:|
| kernel：同一个 FA4，保留约 10% | 7.3× | 7.3× | 7.3× |
| 注意力模块：真实请求中每层 GLOBAL 调用，含 dense 首步、观测和决策 | 4.4× | 2.7× | 0.41× / 0.31× / 0.66× |
| 端到端请求 | 1.16× | 1.15× | 0.79× / 0.67× / 0.89× |

- **为什么端到端只剩约 1.15 倍：** GLOBAL 注意力只占 64K dense 请求时间的 14%（32K 为 9%）。其余是 prefill 约 43%、MoE 专家矩阵乘约占每次 forward 的 40%。
- **为什么 Fan 原版在模块层就慢：** 逐块顺序决策每次 2.3–7.9 ms/层，比 dense 注意力本身（1.5–3 ms/层）还贵，而且每 8 步要重算一次完整 QK（6–11 ms/层）。
- **我们的变体怎么去掉这些开销：**
  - 每个 canvas 只做一次融合观测；
  - DP 决策 0.27 ms/层；
  - 选块放在侧流异步执行；
  - 决策之间沿用块选择。
- 出处：`kernel_bench/README.md`。

### 5.5 试过但没有保留的变体

以下都没有超过简单的 −ln2 阈值：
- 第一层或前两层 GLOBAL 保持 dense；
- canvas 第 24 步之后转 dense；
- 按风险总预算选块：同样保留比例下覆盖的注意力相同；
- 跳过 LOCAL 层：LOCAL 只占 forward 的 2.4%。

出处：`variants_v5/`、`fidelity_v7_budget/`。

### 5.6 为什么 AIME 在 FA4 基线上没有提升空间

结论：AIME 的上下文太短，GLOBAL 注意力在一步里占比太小。即使选块完全免费，稀疏能省的也不到一步的 10%；实际省下的被选块开销和多出来的去噪步数抵消。证据链如下（前三条是实测，第四条是由实测推出的估计）：

1. **上下文长度（实测）：** AIME 提示约 80–380 token，生成最多 8192 token，所以 GLOBAL 注意力的 key 数最多约 8.4K，多数步在 2–6K。
2. **kernel 层（实测，`kernel_bench/README.md`）：** 8K key 时 FA4 dense 的一次 GLOBAL 调用 0.44 ms；block-sparse 保留 50% / 30% / 10% 只快 1.7 / 2.3 / 3.3 倍（64K 时是 2.0 / 3.2 / 7.3 倍）。5 层合计 dense 约 2.2 ms。
3. **模型内整步（实测，`substrate/README.md` 第 3 节）：** 在 CUDA graph 底座上用真实状态重放一次 decoder forward，块选择直接给定、不计选块开销：17K key（已经是 AIME 最长上下文的 2 倍）时 dense 40.7 ms，保留 50% / 30% / 10% 分别是 0.94 / 0.93 / 0.91 倍。AIME 的 key 更少，能省的比例只会更小。
4. **估计：** 8K key 时 GLOBAL 注意力约占一步的 5–6%（2.2 ms 对约 40 ms），更短时更低；保留 50% 时理论上每步最多省约 2–3%。
5. **AIME 面板实测（更新 2、5）：** 实际稀疏度 24–66% 下，每步成本（S/N，摊销值）只有 0.95–1.01，而去噪步数随稀疏度增加 8–27%，请求时间 0.99–1.21，没有一档变快。
6. **对照（64K）：** 同样的方法在 64K 上每步便宜约 16%，GLOBAL 注意力约占 dense 请求的 14%，所以能转化成约 13% 的请求加速。

**关于同学和上周的 AIME 提升：** 结果取决于执行底座。
- 我们上周在 FIXED16 面板上测到 AIME 生成 1.10–1.22×。那次的基线是 HF 原生 eager 路径（SDPA 注意力、没有 CUDA graph），而且包含 LOCAL 跳块。换成 FA4 + CUDA graph 后，这个提升消失了。
- 同学 9/30 PPT 里的 AIME 结果：value_aware 18.4 s/task、37/90，dense 19.6 s/task、44/90，快约 6%，但少对 7 题。那是在他们自己的执行栈上跑的（组里另一页称之为 JAX/FA3 运行），生成上限 2048 token。PPT 没有写 dense 用的是哪种注意力 kernel，所以两边的加速不能直接比较；具体基线需要向同学确认。

### 更新 7（21:00）：AIME 计时的底座缺陷与 v4 修复

**发现：** AIME 面板里，同一个方法每步的平均时间按题目在 36–94 ms 之间变化；同一道题单独跑却稳定在约 35 ms。用 torch 的重编译日志查到原因：
- decoder 的 LOCAL 层会读取编码器的滑动窗口缓存。短 prompt（AIME 只有 80–380 token）在前 3–4 个 canvas 里，这个缓存还没长满 1023 个 token，长度随题目变化。
- 每个新长度乘以 25 个 LOCAL 层，都要重新编译一次。跑几道题后就用完了 torch.compile 的 256 次重编译上限，之后新题前几个 canvas 的 decoder 层退回逐算子执行：每次 forward 约 110 ms，正常是 23 ms。
- 这种回退不会产生新图，所以"计时中捕获新图"的计数器看不到它。
- 长 prompt（LongBench 32K/64K/96K）一开始就填满了窗口，缓存长度固定，不受影响。

**修复：底座 piecewise_v4。** 只对 decoder，把未满的滑动窗口缓存左侧补零到 1023，并给 LOCAL 注意力一个固定形状、原地更新的 mask 屏蔽补齐的槽位。编码器始终看到真实的缓存；窗口满了以后不补齐、不加 mask，与 v3 完全相同。单元测试确认补齐加 mask 后的注意力与不补齐时一致，编码器追加的结果也与不补齐时相同。

**同机对照（dlm2，AIME 30 题 × seed 101/202，dense 与 M3 R6 DP −ln2，各 60 格）：**

| | v3 底座 | v4 底座 |
|---|---|---|
| 每步平均时间（中位数 / 90% 分位 / 最大） | 45 / 82–92 / 110 ms | 33 / 36–37 / 38–50 ms |
| dense 每题平均用时 | 13.6 s | 10.2 s（快 25%） |
| 答对：dense / M3 R6 DP −ln2 | 35 / 32 | 33 / 34 |
| M3 相对 dense 的请求时间（剔除首次编译） | 1.018 | 1.002 [0.918, 1.102] |

**影响与结论：**
- v3 上所有 AIME 面板的绝对时间都被拖慢了，而且有很大一部分计时噪声来自这种回退。同一格的所有方法基本一起受影响，所以配对比较大体仍然公平，但 AIME 的速度比以 v4 重测为准。
- v4 下 dense 基线在 AIME 上快了 25%，是更强、更干净的基线。精度差别在跨运行噪声内：数值上的微小变化让生成轨迹略有不同。
- 我们的方法在 AIME 上仍与 dense 持平（1.002），结论不变。
- 64K 的结果不受影响。
- 第二处待修：canvas 追加（每个 canvas 把 256 个 token 送进编码器）仍是逐算子执行，每次约 66 ms，占 AIME 请求的约 20%。官方编译路径会编译它，下一步把它分段编译进 CUDA graph（v5）。
- 协议 `v27_aime_v4_check`（`specs/v27_aime_v4_check.json`），数据 `aime_v4_check/summary.md`。

### 更新 11（23:50）：文献与组内进展——稀疏注意力导致的步数/输出变长

**dLLM 稀疏注意力论文都用固定步数和固定输出长度，所以没有测到这个问题：**
- SparseD（ICLR 2026，arXiv 2509.24014）：前若干步 dense，之后复用稀疏模式；64K、1024 步时最高 1.50×。
- PulseCol（arXiv 2605.20813）：按列稀疏，只在早期阶段刷新索引；LLaDA-1.5、1024 步固定，相对 FlashAttention-2 在 4K/8K/16K/32K/64K 为 1.07/1.14/1.29/1.55/1.95×，并明确不改步数和输出长度。
- Focus-dLLM（arXiv 2602.02159）：按过去置信度预测要解码的位置，只剪 prompt 块、保留全部回答 token 和 attention sink；29× 是相对不带缓存的 vanilla，生成长度和步数固定为 256。
- 这些设置（无 KV cache、很多步、固定步数）与 DiffusionGemma（有 KV cache、每 canvas 约 10 步自适应停止）差别很大，注意力在我们这里占比小得多，而且步数会随轨迹变化。

**自回归推理模型上有同样的现象：**
- Lil（arXiv 2601.03043）：稀疏注意力让推理输出最多变长 90%，每步更快但总时间更长；其修法 Guardian 是基于信息增量的早停，对 dense 同样有效，因此不是注意力方法本身的贡献。
- LessIsMore（arXiv 2508.07101）：跨 head 统一选 token，并固定留 25% 预算给最近的 token；AIME-24 上把输出变长从 Quest 的 +103% 降到 +7%。
- 共同的解释：选块丢失的信息在长推理中累积，模型通过多写来"补"。这提示我们的输出变长可能与跳过了模型自己生成的 token 有关，因此 E3 加入"生成 token 不跳"的变体。

**组内（只引用 PPT 原文，组内测量不是公开文献）：** 组里 megakernel.pptx 9/23–9/30 页（value-aware / temporal sensitivity 部分）记录了同样的"高稀疏度去噪步数膨胀"：RULER4K、70% 稀疏度时每 canvas 16.45 步（dense 4.00 步）。他们试过前 1 步 dense、后几步 dense、条件纠正、放宽结束条件，均无效；LoSA（arXiv 2604.12056）式的 token 保护有希望；目前最好的是按 top-1 翻转加权保护 query（T），70% 稀疏度下 6.78 步、89.7%，但端到端 0.840 s 仍慢于原生 dense 的 0.584 s。按查询敏感度保护来抑制步数膨胀是同学的方向，列为**合作候选**，不作为我们的 novelty。分支方面，9/27 之后只有 `chw/value_aware`（9/30，JAX 行重排 grouping 与 AIME25 评测文件）有新提交。

**我们自己 9/21 的对照（`research/adaptive-trajectory-characterization-20260921`）：** 同一进程内 dense 完全确定；换一次模型加载，dense 的去噪次数比值中位数 1.165、p90 1.64。在这个噪声下，G60/G75 的步数增加只在 AIME G75 上显著（+11%）。这解释了为什么我们的 N 在不同题组上忽高忽低：请求级结论需要更多样本，每 canvas 步数 NC 比总步数 N 稳定，是更好的诊断量。

**新指标：每 canvas 解码时间 S/C。** S/N 是摊销到每步的成本，步数越少它越被高估（每个 canvas 的固定开销被摊到更少的步上）；S/C = 每步成本 × 每 canvas 步数，同时反映两者，是比较这些变体最干净的量。请求时间 ≈ S/C × canvas 数 + prefill。

**结论：**
- **32K 上存在一条清楚的权衡：** 跳得越多（阈值越激进），每步越便宜，但每个 canvas 的步数越多；阈值 0 还掉了 5 题。让选块图更"新"（R3、第 2 步观察）或更保守（−2ln2）都能把每 canvas 步数压回到约 1.02–1.04，但每步节省也随之变小。
- **两者相乘后，32K 的净收益最多约 3%：** 最好的 obs2 / −2ln2 / 阈值 0 的每 canvas 解码时间为 0.96–0.97，置信区间都跨过 1；主线 −ln2 为 1.018，即每步的节省被多走的步完全抵消。请求级 W 最好 0.97，同样不显著。
- **生成 token 不跳（po）没有明显帮助：** 32K 上输出长度本来就几乎不变（E1 中 T 为 1.007），步数增加主要来自每个 canvas 内部，而不是输出变长。
- **对比 64K（traj_t1，同一指标）：** M3 −ln2 每 canvas 解码 0.866 [0.829, 0.899]，B 0.861 [0.821, 0.900]，−2ln2 0.877，收益稳定在 12–14%。所以 64K 是这个方法真正有效的区间，32K 基本是盈亏平衡。64K 的请求级结论取决于输出长度（canvas 数），而它的噪声很大（见更新 11）。
