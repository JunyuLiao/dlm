# 进度文档（2026-09-30）：DiffusionGemma 上 Fan 的 M1/M2/M3 稀疏注意力

写给没跟进本周实验的同学：先讲清楚我们在做什么、方法名里每个参数是什么意思、实验怎么设的，再讲结果和结论。所有数字都来自本目录下已推送的结果文件，出处标在各节。

---

## 1. 一句话总结

- **长上下文（56–76K tokens）：** 在最快的官方 dense 基线（FlashAttention-4）上，我们的稀疏方法端到端请求快约 13–14%，去掉 prefill 后解码快约 21%，精度不降。结果在三个独立面板里复现。
- **短上下文（AIME、10–19K 的 LongBench）：** 没有加速。AIME 120 格上，我们选定的 M3 R6 DP −ln2 精度与 dense 完全持平（65 vs 65），只有 B 有下降趋势。加长度门限（短上下文直接走 dense）后，精度与 dense 逐格一致。
- **Fan 原版 M1/M2/M3：** 在所有长度上都比 dense 慢，原因是选块本身的开销超过了省下的注意力。
- **新颖性：** 最接近的已有工作是 SparseD（ICLR 2026），与我们的 B 撞车。移植到同一 FA4 kernel 的正面对比显示，速度上我们与 SparseD 最好的一档没有显著差别（64K 0.957 [0.872, 1.072]），按撞车处理；精度都在噪声内（更新 3）。
- **AIME：** 同等稀疏度（实际 24–41%）下我们的选块和 SparseD 都不掉分，但在 FA4 基线上都没有提速（更新 2）。实际稀疏度到 66% 时我们的选块显著掉分（23 对 34），SparseD 仍是 29：高稀疏度区我们不如 SparseD（更新 5）。

## 2. 背景：我们在加速什么

**模型与解码方式**
- 模型：DiffusionGemma-26B-A4B（MoE，激活参数约 4B）。
- 解码方式：以 256 个 token 为一个 canvas 块，块内反复去噪。每个 canvas 的去噪步数由模型自带的置信度停止规则决定（置信度阈值 0.005、stability 1、最多 48 步），这就是"原生自适应停止"。一个 canvas 完成后追加到上下文，再生成下一个。

**注意力结构**
- 30 层 decoder 里，5 层是 GLOBAL 注意力（第 5/11/17/23/29 层）：看全部上下文，head_dim 512，16 个 query head、2 个 KV head。
- 其余 25 层是 LOCAL 注意力：滑动窗口只看最近 1024 个 key。
- 长上下文里真正随上下文变贵的只有 5 层 GLOBAL，所以**我们只稀疏化 GLOBAL 层**，LOCAL 层一直保持 dense。

**"稀疏"在这里具体是什么**
- 每次 GLOBAL 注意力调用里，query 是 canvas 的 256 个位置，key 是整个上下文。把 key 按 64 个一组切成块（tile），query 按 128 个一组，稀疏注意力就是跳过一部分 (query 块, key 块) 组合。
- 本文的"保留比例"指保留下来的上下文 key 块占多少，"稀疏度" = 1 − 保留比例。
- canvas 自己的 key 块总是保留。每个 canvas 的第一步总是 dense。

## 3. 方法名词表：M3 R6 DP −ln2 这些都是什么意思

**Fan 的三个方法（组里的核心方法，每次比较都必须包含）**
- **M1：** 选块时估计"跳过这个块，注意力输出会变多少"。用到的信息有：
  - 历史上观测到的 QK 分数（每隔几步观测一次，不是每步都算）；
  - 当前的 V 投影到 32 维后的值；
  - 当前参考范数和 query 敏感度 T。

  风险低于阈值的块就跳过。输出始终用当前的 QK 和原始 V 精确计算，选块只决定跳过哪些块。
- **M2：** 同 M1，但 V 用块内均值代替投影 V（本周跑的是 M2c，即 compact pooled 版本）。
- **M3：** 同 M1，但不是每步都重新决策，而是每 R 步决策一次，中间沿用上一次的块选择。

**参数与变体后缀**

| 写法 | 含义 |
|---|---|
| R1 / R3 / R6 / R12 | 每 1 / 3 / 6 / 12 步做一次选块决策（M1 = R1） |
| A8 / A64 | 每 8 步 / 每个 canvas 一次，重新观测一次 QK 分数。A64 的实际效果是每个 canvas 只观测一次，而且观测与该 canvas 第二步的 dense 计算融合在同一个 kernel 里（fused observation） |
| DP（dense-prefix） | 风险相对"所有更早的块都保留"的状态来算，而不是相对"已保留的块"。这样所有块可以并行判断，一次决策从约 2–8 ms/层降到 0.27 ms/层 |
| −ln2 / −2ln2 / +ln2 | 阈值移位：加在对数风险阈值上。负数保留更多块（更保守），正数跳过更多。默认阈值是 −3.18，−ln2 后是 −3.874 |
| B | "观测一次后固定"：每个 canvas 第一步 dense，第二步观测并选块，之后整个 canvas 都用这张块选择，不再更新（hold-only） |
| async / rp | 选块计算放到另一条 CUDA 流上异步执行 / 流水线化；不改变决策，只省时间 |
| gate32k | 长度门限：上下文 key 数少于 32768 时整层直接走 dense |
| Fan 原版 | 即 M1 R1 A8、M2c R1 A8、M3 R3 A8，也就是按原始定义不加任何工程优化的版本 |

所以 **"M3 R6 DP −ln2"** 读作：
- M3，每 6 步决策一次；
- 每个 canvas 融合观测一次（A64）；
- 用 dense-prefix 方式并行算风险；
- 阈值比默认保守 ln2（多保留一些块）。

**典型保留比例（稀疏度）**
- 取自保真度诊断，是开发题上的中位数，只统计固定 map 期间的 GLOBAL 调用：

  | 方法 | 64K 保留（稀疏度） | 32K 保留（稀疏度） |
  |---|---:|---:|
  | B | 10%（约 90%） | 15%（约 85%） |
  | M3 R6 DP，默认阈值 | 7%（约 93%） | 12%（约 88%） |
  | M3 R6 DP，−ln2 | 12%（约 88%） | 21%（约 79%） |
  | Fan 原版 M1 | 15%（约 85%） | 22%（约 78%） |

- AIME 前缀短，稀疏度只有 2–12%。
- 整体注意力的实际稀疏度更低：每个 canvas 的前两步是 dense，25 层 LOCAL 始终 dense。

## 4. 实验设置：怎么保证对比公平

**Dense 基线**
- 用官方 FlashAttention-4（vLLM 的 flash-attn cute 构建）的 block-sparse 接口，把所有块都保留，结果与 FA4 dense 逐位一致，而且快 1–2%。
- 所有稀疏方法跑的是同一个 FA4 kernel，与 dense 的区别只在跳过了哪些块。
- HF 模型默认的 PyTorch SDPA 在 head_dim 512 下 kernel 慢 5.8–7.5 倍，端到端慢 1.6–2.2 倍，所以不用它当基线，否则加速会被夸大。

**执行底座：所有方法相同**
- decoder 用分段 CUDA graph 编译（vLLM 的做法），prompt prefill 用 FA4。
- 还修掉了官方实现的一个低效之处：每一步都把整个 KV 缓存重新拼接一遍。修复后生成的 token 逐位不变，所有方法都快 5–6%。

**流程**
- 每个面板在生成前冻结协议（题目、seed、方法、机器分配）。
- 同一道题的所有方法在同一块 GPU 上跑（共 2 块 H100）。

**统计**
- 每格（题目 × seed）只取第一次输出。
- 速度用与 dense 配对后的几何平均比值，95% 置信区间按题目聚类 bootstrap。
- 精度报告答对格数和"+只有该方法对 / −只有 dense 对"，用符号检验。
- 同时报告：
  - 请求墙钟 W；
  - 去掉 prefill 的解码时间 S；
  - prefill 比值 P：所有方法都约等于 1，说明没有改动 prefill；
  - 去噪步数。

**数据集**

| 数据 | 来源 | 长度 | 题数 | 每个方法的格数 |
|---|---|---|---:|---|
| LongBench-v2 标准池 | 官方题 | 10–19K tokens | 12 | 3 seed = 36 格 |
| LongBench-v2 32K 档 | 官方题，按自然长度分档，不截断 | 28–40K tokens | 12 道正式题（另 12 道开发题不评分） | 3 seed = 36 格 |
| LongBench-v2 64K 档 | 同上 | 56–76K tokens | 12 道正式题（另 12 道开发题不评分） | 3 seed = 36 格 |
| AIME26 | 全部题 | — | 30 | 最终面板 4 seed = 120 格；早先面板 2 seed = 60 格 |

- seed 为 101/202/303（AIME 加 404）。

- **B 是唯一下降的：** 58/120，120 格下已不显著；早先 60 格面板里是 26 vs 35，显著。

- 出处：`final_panel_f1/README.md`。

### 5.4 加速在三层上怎么缩小（64K，论文口径）

| 层级 | B | M3 R6 DP −ln2 | Fan 原版 M1 / M2c / M3 |
|---|---:|---:|---:|
| kernel：同一个 FA4，保留约 10% | 7.3× | 7.3× | 7.3× |
| 注意力模块：真实请求中每层 GLOBAL 调用，含 dense 首步、观测和决策 | 4.4× | 2.7× | 0.41× / 0.31× / 0.66× |
| 端到端请求 | 1.16× | 1.15× | 0.79× / 0.67× / 0.89× |

- **为什么端到端只剩约 1.15 倍：** GLOBAL 注意力只占 64K dense 请求时间的 14%（32K 为 9%）。其余是 prefill 约 43%、MoE 专家矩阵乘约占每次 forward 的 40%。
- **为什么 Fan 原版在模块层就慢：** 逐块顺序决策每次 2.3–7.9 ms/层，比 dense 注意力本身（1.5–3 ms/层）还贵，而且每 8 步要重算一次完整 QK（6–11 ms/层）。
- **我们的变体怎么去掉这些开销：**
  - 每个 canvas 只做一次融合观测；
  - DP 决策 0.27 ms/层；
  - 选块放在侧流异步执行；
  - 决策之间沿用块选择。
- 出处：`kernel_bench/README.md`。

### 5.5 试过但没有保留的变体

以下都没有超过简单的 −ln2 阈值：
- 第一层或前两层 GLOBAL 保持 dense；
- canvas 第 24 步之后转 dense；
- 按风险总预算选块：同样保留比例下覆盖的注意力相同；
- 跳过 LOCAL 层：LOCAL 只占 forward 的 2.4%。

出处：`variants_v5/`、`fidelity_v7_budget/`。
