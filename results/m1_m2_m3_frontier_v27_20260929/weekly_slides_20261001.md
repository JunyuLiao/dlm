## 第 2 页：时间都花在哪：为什么单请求下注意力稀疏的收益有上限

**【正文顶部】** 64K dense 一个请求约 13.1 s（三台 H100、piecewise_v3–v5 实测平均）；32K 约 9.7 s

**【主表】（64K，占请求时间）**

| 部分 | 时间 | 占比 | 稀疏注意力能否省 |
|---|---:|---:|---|
| prompt prefill + 准备 | 约 4.6 s | 35% | 否（不在本方法范围） |
| 解码：5 个 GLOBAL 注意力层 | 约 2.8 s | 21% | **是**：M3 降到约 1.2 s |
| 解码：MoE 专家 | 约 2.4 s | 18% | 否（每步读约 46 GB 专家权重，已到 HBM 带宽上限） |
| 解码：采样（262K 词表） | 约 0.9 s | 7% | 否 |
| 解码：其他（投影、LOCAL、norm、canvas 追加） | 约 2.4 s | 19% | 否 |

**【要点】**
- 即使注意力完全免费、步数不变，单请求的上限也只有 64K 约 −21%、32K 约 −16%；我们已拿到 −12% / −6%。
- M3 剩下的约 1.2 s 注意力（估计）：每个 canvas 前 2 个 dense 步约 0.5 s、稀疏执行约 0.5 s、观测/决策约 0.2 s。
- AIME（上下文 ≤ 约 8K）上 GLOBAL 注意力只占每步约 4–7%：注意力稀疏在 AIME 上天然没有多少空间。

**【Speaker notes】**
- 每步构成（32K，dense，`substrate/time_breakdown.json`，v2 时期，KV 拼接已在 v3 去掉）：forward 约 32 ms：MoE 专家矩阵乘 12.8 ms、GLOBAL 注意力 7.2 ms、其余矩阵乘 3.5 ms、LOCAL 0.8 ms、其他约 4 ms；加上采样约 4.6 ms。
- MoE：128 个专家、每 token 选 8 个；一步 256 个 canvas token × 8 = 2048 次分配，几乎所有专家都会被用到，所以每步要读全部专家权重（约 46 GB），12.8 ms 已接近 H100 的 HBM 带宽极限。
- GLOBAL 注意力（CUDA event 直接计时，`kernel_bench/module_profile_*`）：dense 每层 1.46 ms（32K）/ 2.95 ms（64K）；M3 R6 DP −ln2 摊到每步：32K 4.3 ms、64K 5.5 ms（dense 7.3 / 14.75 ms）。
- 每步解码时间（摊销，72 格平均）：32K dense 37.3 ms、M3 34.7、B 33.5；64K dense 45.3、M3 37.2、B 36.1；AIME dense 30.7、M3 31.4。

## 第 3 页：去掉每个 canvas 的一个 dense 步（carry0）：64K 端到端快 15%，32K 快 9%

**【正文顶部】** 与 E4 完全相同的 288 格（LongBench-v2 32K/64K 各 24 题 × seed 404–909）、同机、同底座 v5 · dense = FA4

|---|---|---:|---:|---|---:|---:|
| M3 R6 DP −ln2（上一页的主结果） | 0.879 [0.818, 0.927] | 0.807 | 77 | 0.942 [0.900, 0.984] | 0.920 | 86 |
| **M3 R6 DP −ln2 + carry0** | **0.853 [0.802, 0.895]** | **0.775** | 76 | **0.907 [0.858, 0.952]** | **0.878** | 92 |

| B + stable1 门控 | 0.889 | 0.826 | 79 | 0.938 | 0.920 | 88 |

**【要点】**
- carry0：每个 canvas 的第 0 步不再 dense，改用上一个 canvas 最后的选块图（新增的块全部保留）；第 1 步照常 dense + 观测，之后用新图。每个 canvas 少一个 dense 步。
- 与不带 carry0 的 M3 直接配对：64K 再快 2.9%（0.971 [0.939, 1.001]），32K 再快 3.7%（0.963 [0.914, 1.011]）；精度不降（不一致格 64K 7/8、32K 15/9）。

**【Speaker notes】**
- 协议 `v27_lb_overhead_e5_1c93b97271a3a266`（`specs/v27_lb_overhead_e5.json`），部署提交 758723513；2016/2016 次运行成功，计时中无新 CUDA graph；dense、M3、B 三臂与 E4 逐 token 相同（各 288/288），所以本页与上一页可直接对照。
- 收据核对：carry0 每个请求只在 canvas 0 做 dense 引导（5 层 × 1 次），其余 canvas 的第 0 步都消费了上一 canvas 的图（carried_first_calls = 5 ×（canvas 数 − 1））；stable1 在 225/288 个 M3 请求里触发，共把 12,810 次 GLOBAL 调用转成 dense。
- 与 E1 的跨 canvas 复用（K=4，整个 canvas 都用旧图）不同：carry0 只在第 0 步用旧图，第 1 步就刷新，所以没有"旧图让步数变多"的问题（每 canvas 步数 64K 0.98、32K 1.00）。

## 第 7 页：批量服务时注意力占比与稀疏收益（单次 forward 测速，非端到端）

**【正文顶部】** 64K 真实状态（LongBench-v2 64K 第 1 题，71,772 个 key，第 6 次 decoder 调用）复制成 batch B · 整个 forward 用 CUDA graph 重放计时 · 稀疏为合成保留图（不含选块开销）

**【主表】**

| batch | dense forward | 保留 12% | 只留 canvas | prefix 注意力占比 | 保留 12% 时每次 forward 省 |
|---:|---:|---:|---:|---:|---:|
| 1 | 54.4 ms | 41.8 | 40.0 | 26% | 23% |
| 2 | 70.8 | 57.6 | 55.3 | 22% | 19% |
| 4 | 117.7 | 93.7 | 88.7 | 25% | 20% |
| 8 | OOM | | | | |

**【要点】**
- 原以为批量服务里 MoE 权重读取被分摊、注意力会成为大头；实测 64K、batch ≤ 4 时注意力占比不变（22–26%），稀疏的单步收益也稳定在约 20%。
- 原因：batch=1 时 FA4（256 个 query）吃不满 GPU，batch 变大后注意力反而更高效；MoE 也从带宽受限变成算力受限。
- 所以"换批量服务场景就能大幅放大收益"不成立（至少在 64K、batch ≤ 4）。

**【Speaker notes】**
- 脚本 `scripts/v27_batch_step_bench.py`（提交 02eead519），dlm2，E4 运行目录与部署；数据 `batch_scaling/`。
- 计时口径：eager 的整次 decoder forward（含每次调用的 K/V 拼接，1.2/2.4/4.7 ms）一次性 CUDA graph 捕获后重放，CUDA event 取 15 次中位数；采样另测 2.5/4.8/9.4 ms。
- 局限：只测了 64K 一个状态；batch 8 时复制的 64K 缓存放不下；合成保留图、不含选块开销；不是端到端，也不是真实服务。

| MAGE（2602.14209） | 块的第一步做精确注意力选 top-k，整块复用；副流异步选块 | 7–8B 块扩散，32 token 块 × 固定 32 步，128K 端到端 6.82× | ≈ B（撞车）；大倍数来自 dense 小模型 + 128K + 固定步 |
| PulseCol（2605.20813） | 列稀疏，早期周期刷新 | 1024 步固定 | ≈ M3 的定期刷新 |
| HERALD（2606.21633） | 批量块扩散服务：每块选一次 KV、CPU-GPU 协同取 KV | 批量服务，5% KV 预算，解码吞吐 2.28× | 批量服务方向的直接相关工作 |
| Focus-dLLM、LoSA、FlashBlock | 按置信度/稳定 token 裁剪或复用 | 固定步数/长度 | 部分相关 |
| Lil（2601.03043）、LessIsMore（2508.07101） | 稀疏注意力导致推理输出变长 | 自回归推理模型 | 我们在 E4 中没有观察到输出变长 |

**【要点】**
- 方法层面"每块选一次、复用"的思路已被 SparseD / MAGE / HERALD 覆盖；"看 V 的选块更好"没有数据支持（E8：AIME 固定 70% 稀疏度下，没有任何 V 项优于只看注意力质量；64K 的同类对照 E9 今晚出结果）。
- 我们站得住的是：生产级 MoE dLLM（DiffusionGemma，原生自适应停止 + KV cache）+ 最强官方基线（FA4 + CUDA graph）+ 大样本协议下，端到端 64K −12%、32K −6%，精度不降；以及"MoE 权重带宽决定上限"的成本分析。
- 可能的论文方向（待讨论）：(1) 批量服务（第 7 页：64K、batch ≤ 4 时没有放大收益；HERALD 部分撞车）；(2) 自适应停止下 dLLM 加速的评测方法学（大样本、dense 对照方差）；(3) 与同学的 query 敏感度方向合作。
