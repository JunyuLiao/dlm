## P1　长上下文主结果：64K 端到端快约 13%，精度不降

**【正文顶部】** LongBench-v2 自然长度 32K 档（28–40K token）/ 64K 档（56–76K token）· 各 12 题 × 3 seed = 每档 36 格/方法 · dense = FA4 · 同一格的所有方法同机配对

**【正文】**

| 方法 | 64K 请求 W | 64K 解码 S | 64K 答对（dense 18） | 32K 请求 W | 32K 答对（dense 28） |
|---|---|---:|---:|---|---:|
| 原版 M1 / M2c / M3 | 1.27 / 1.49 / 1.12 | 1.41 / 1.79 / 1.18 | 20 / 16 / 21 | 1.33 / 1.33 / 1.15 | 25 / 27 / 29 |
| B | **0.864** [0.825, 0.905] | 0.788 | 20 | 0.935 [0.862, 1.016] | 31 |
| **M3 R6 DP −ln2** | **0.869** [0.805, 0.933] | **0.783** | **23** | 0.902 [0.780, 1.015] | 31 |

**【说明】**
- 64K 上请求时间减少约 13%，去掉 prefill 后解码减少约 22%，精度不降。
- 32K 上不显著；原版在两档都更慢。

**【讲者备注】**
- **缩写：**
  - W：请求墙钟时间比，含 prefill；S：去掉 prompt prefill 后的解码时间比。
  - 格：一个（题目, seed）组合，每格只取第一次输出。
  - 比值是配对后的几何平均，置信区间按题目聚类 bootstrap（4000 次）；答对差用配对符号检验。
- **方法名：**
  - 原版：M1 R1 A8 / M2c R1 A8 / M3 R3 A8。
    - M1 用历史 QK + 投影到 32 维的当前 V 估计"跳过一个块会让输出变多少"，每步决策，每 8 步重新观测一次 QK；
    - M2c 把投影 V 换成块内均值；
    - M3 每 3 步决策一次。
  - B：每个 canvas 第 1 步 dense，第 2 步观测并选块，之后整个 canvas 沿用。
  - M3 R6 DP −ln2：每 6 步决策一次；每个 canvas 一次融合观测（A64）；风险相对"所有更早的块都保留"来算，可以并行（DP，0.27 ms/层）；对数阈值比默认（−3.18）低 ln2，变成 −3.874，所以多保留一些块。
  - 所有方法都只稀疏 5 个 GLOBAL 层（第 5/11/17/23/29 层，head_dim 512）；25 个 LOCAL 层（窗口 1024）保持 dense。
- **基线：** FA4（vLLM 的 flash-attn cute 构建）的 block-sparse 接口，保留全部块。
  - 它与 FA4 dense 逐位一致，并快 1–2%。
  - 所有稀疏方法跑同一个 kernel，只差跳过了哪些块。
  - HF 默认的 SDPA 在 head_dim 512 下端到端慢 1.6–2.2 倍，不用它当基线，否则加速会被夸大。
- **底座：** decoder 分段 CUDA graph（vLLM 式），prefill 用 FA4，每步不再重新拼接 KV。所有方法相同。
- **生成设置：** 原生自适应停止（置信度 0.005、stability 1、每个 canvas 最多 48 步），thinking 开启，最多 8192 token；评分用 NeMo LongBench 多选评分器。
- **复现：**
  - 64K 速度复现了 5 次：0.868 / 0.872 / 0.869 / 0.865 / 0.821。
  - 前 4 次在同一批机器上生成的 token 完全相同，所以答对数也相同，不算精度的独立复现。
  - 新机器 dlm2 上答对是 18 对 21，在噪声内。
  - 跨机器同一方法的答对数约差 ±3/36。
- **其他：**
  - 64K 上 M3 答对 +5/−0，p = 0.06，只说"不降"，不宣称提升。
  - 加 32K 长度门限（短上下文直接走 dense）后，10–19K 的 LongBench 标准池与 dense 完全一致，额外开销约 0.5%。
- **协议与数据：** `v27_final_lb_f1`（生成前冻结，dllm + mpk 两块 H100），`final_panel_f1/`。

## P2　为什么端到端只有 1.15×：加速在三层上怎么缩小

**【正文顶部】** 64K · 同一个 FA4 kernel · kernel 级（单次 GLOBAL 调用）→ 注意力模块级（真实请求中逐次计时）→ 端到端

**【正文】** 图：`fig_three_levels.png`

**【说明】**
- kernel 层面保留约 10% 的块时快 7.3 倍，到注意力模块剩 2.7–4.4 倍，到端到端请求只剩约 1.15 倍。
- 原因：GLOBAL 注意力只占 64K dense 请求时间的 14%，prefill 约占 43%。
- 原版在模块层就已经比 dense 慢：选块本身比注意力还贵。

**【讲者备注】**
- **kernel 级**（`kernel_bench/README.md`）：
  - 形状：一层 GLOBAL 调用，16 个 query head × 256 个 canvas query，2 个 KV head，bf16；
  - 计时：CUDA events，取 50 次中位数；
  - 8K→128K 时，保留 10% 的加速从 3.3× 增到 8.3×。
- **模块级**（`kernel_bench/module_profile_64k.jsonl`）：在真实 64K 请求里，用 CUDA events 包住每次 GLOBAL 调用及其各部分。
  - 平均每次调用：B 0.68 ms，M3 R6 DP −ln2 1.09 ms，dense 2.95 ms。
  - 这个平均值包含每个 canvas 的 dense 首步、融合观测和选块决策。
- **原版为什么慢：**
  - 逐块顺序选块每次 2.3–7.9 ms/层，比 dense 注意力本身（1.5–3 ms）还贵；
  - 每 8 步还要重算一次完整 QK（6–11 ms/层）。
  - 我们的变体把这些开销去掉了：每个 canvas 一次融合观测、DP 并行决策、选块放副流、决策之间沿用。
- **时间构成**（`substrate/time_breakdown.json`，64K dense 请求 10.2 s）：
  - prefill 43%，decoder forward 43%（其中 GLOBAL 注意力 14%），其余是采样、canvas 追加和主机开销；
  - 一次 forward 里 MoE 专家矩阵乘约占 40%。
- **剩余空间：** 我们的方法在 64K 上一条请求约 7.8 s，其中 prefill 约 4.35 s（我们没有动），剩下的 GLOBAL 注意力只有约 0.34 s。所以即使把注意力全部省掉，请求最多再快约 4%。
- **口径：** 论文里三层都要报；只报 kernel 会把效果夸大约 6 倍。

## P3　新颖性：与 SparseD 正面对比（同一个 FA4 kernel）

**【正文顶部】** LongBench-v2 32K/64K（与 P1 同题）× 3 seed = 每档 36 格/方法 · SparseD（ICLR 2026）移植到同一 FA4 kernel 与底座 · 504 次运行

**【正文】**

| 方法 | 64K 请求 W | 64K 每步成本 | 64K 步数 | 64K 答对（dense 18） | 32K 请求 W |
|---|---|---:|---:|---:|---|
| 我们 M3 R6 DP −ln2 | **0.865** [0.804, 0.929] | 0.836 | 0.940 | 23 | 0.912 |
| B | **0.860** [0.819, 0.903] | 0.795 | 0.991 | 20 | 0.931 |
| SparseD 保留 10%，前 1 步 dense | 0.905 [0.816, 0.997] | 0.842 | 1.017 | 21 | 0.916 |
| SparseD 保留 20%，前 1 步 dense | 0.926 [0.816, 1.036] | 0.864 | 1.041 | 21 | 1.018 |
| SparseD 论文默认（保留 30%，前 10 步 dense） | 1.005 | 1.000 | 1.032 | 18 | 1.025 |

直接配对，我们 / SparseD 保留 10%：请求 **0.957 [0.872, 1.072]**，每步成本 0.993。

**【说明】**
- 速度上与 SparseD 最好的一档没有显著差别：按撞车处理。
- SparseD 论文默认的"前 20% 步 dense"在自适应停止下基本等于 dense（每个 canvas 只走 10–12 步）。
- 精度都在噪声内。

**【讲者备注】**
- **SparseD 原论文：** 前 20% 的步用完整注意力，之后按块平均注意力分数一次性选出模式（保留 30%），并一直复用。原论文用 FlexAttention，在 LLaDA / Dream 上固定 32–1024 步。
- **移植方式**（`v20_controls.sparsed_bitmap`，有单元测试，标明是移植版）：
  - 在 FA4 的 128×64 tile 上做平均池化，每个（head, query 块）保留排名前 XX% 的 prefix tile；
  - canvas 自己的 key 块始终保留；
  - 算模式那一步的输出仍用 dense，之后沿用到 canvas 结束。
- **与原实现的差异：**
  - tile 是 128×64，原论文是块 128；
  - canvas key 始终保留；
  - skip 按步数给：10 步 = 48 步上限的 20%；
  - kernel 用 FA4，不是 Flex。
- **稀疏度可比：** 我们的 M3 R6 DP −ln2 在 64K 开发题上约保留 12% 的块，与 SparseD 保留 10–20% 的两档相当。
- **判断标准（事先定的）：** 同等速度下精度不优于 SparseD、同等精度下也不更快，就按撞车处理。按这个标准，速度这一项是撞车。
- **收据核对：**
  - SparseD 每个 canvas 每层观测一次，其余步沿用；
  - "前 10 步 dense"在一条请求的 330 次调用里有 300 次是 dense；
  - 504 条请求全部成功，计时中没有捕获新图。
- **运行说明：** dllm 那一半因为早先误杀的 worker 留下没有结束标记的启动记录（没跑出任何一格），用同一冻结协议、同一部署在新目录重跑后合并评分。
- **协议与数据：** `v27_long_lb_sparsed_c1`，`sparsed_panel_c1/`。

## P4　AIME：稀疏度对精度和速度的影响（与同学同口径）

**【正文顶部】** AIME26 全部 30 题 · 目标稀疏度 30/40/50%（3 seed = 90 格）与 70/80%（2 seed = 60 格）· 我们：按风险取 top-k · SparseD 移植 · dense = FA4

**【正文】** 图：`fig_aime_sparsity.png`

**【说明】**
- 实际稀疏度 41% 以下，两种选块都不掉分；到 66% 时我们的选块显著掉分（23 对 34），SparseD 只降到 29。
- 没有一档变快：AIME 上下文最多约 8K key，GLOBAL 注意力只占一步约 5–6%，而稀疏度越高去噪步数越多。

**【讲者备注】**
- **数字：**

  | 实际稀疏度 | 我们：答对 / 请求 W / 步数 | SparseD：答对 / 请求 W / 步数 |
  |---|---|---|
  | 23–24% | 49/90（dense 49）/ 1.076 / 1.087 | 48/90 / 0.988 / 0.978 |
  | 32% | 48/90 / 1.086 / 1.106 | 47/90 / 1.034 / 1.045 |
  | 40–41% | 48/90 / 1.062 / 1.078 | 47/90 / 1.021 / 1.025 |
  | 56–57% | 28/60（dense 34）/ 1.196 / 1.231 | 29/60 / 1.081 / 1.107 |
  | 65–66% | **23/60（+3/−14，p ≈ 0.013）**/ 1.206 / 1.269 | 29/60 / 1.075 / 1.094 |

- **定义：**
  - **实际稀疏度**按构造计算：被跳过的 GLOBAL key 块占全部 GLOBAL 调用的比例。canvas 块总保留，每个 canvas 第一步 dense，所以低于目标值。
  - **topk 是我们为比较加的变体：** 原版方法没有"目标稀疏度"旋钮，阈值版在 AIME 上只稀疏 2–12%。topk 用 M1-DP 风险排序，每个（head, query 块）保留风险最高的块，其余同 M3 R6 DP。
- **为什么 AIME 没有提升空间（前三条实测）：**
  1. 8K key 时 FA4 dense 一次 GLOBAL 调用 0.44 ms，保留 50% 只快 1.7 倍。
  2. CUDA graph 底座上重放整步，选块不计成本：17K key 时保留 10% 每步也只省 9%。
  3. 本页实测每步成本 0.95–1.01，步数随稀疏度增加 8–27%。
  4. 对照：64K 上每步省约 16%，才换来约 13% 的请求加速。
- **最终 AIME 面板**（120 格，选定配置 M3 R6 DP −ln2）：答对 65 对 65；请求 1.008 [0.957, 1.063]，已剔除计时中捕获新图的配对。早先汇报的 0.971 被 dense 的两条异常请求拉低，已更正。
- **与同学和上周的结果：**
  - 我们上周在 HF 原生 eager 路径（SDPA、无 CUDA graph、含 LOCAL 跳块）上测到 AIME 1.10–1.22×，换成 FA4 + CUDA graph 后消失。
  - 同学 9/30 PPT 的 AIME 结果：value_aware 18.4 s/task、37/90，dense 19.6 s/task、44/90。那是他们自己的执行栈（JAX/FA3，生成上限 2048 token），PPT 没写 dense 的注意力 kernel，两边不能直接比，需要向同学确认。
- **负结果的处理：** 高稀疏度下风险 top-k 不如 SparseD，原因还没分析，组会后再查；先如实记为负结果。
- **协议与数据：** `v27_aime_sparsity_t1`、`v27_aime_sparsity_hi`，`aime_sparsity_panel_t1/`、`aime_sparsity_panel_hi/`。

## P5（可选）　补充：M2 的变体与更长上下文

**【正文顶部】** M2：LongBench-v2 32K/64K × 3 seed，新机器 dlm2 · 96K：84–104K 自然长度 12 题 × 2 seed · 128K：112–144K · 单卡 H100 80GB

**【正文】**

| 实验 | 方法 | 请求 W | 说明 |
|---|---|---|---|
| M2 变体，64K | M2c R6 DP −ln2（新） | **0.847** [0.744, 0.937] | 原版 M2c 是 1.44（更慢） |
| M2 变体，64K | M3 R6 DP −ln2（同面板） | 0.821 [0.729, 0.902] | 与 M2c 在置信区间内重叠 |
| 96K（能跑的 12 格） | M3 R6 DP −ln2 | 0.948 [0.863, 1.024] | 每步成本 0.818，但步数 +18% |
| 128K | 所有方法，包括 dense | — | 预填充 OOM |

**【说明】**
- M2 放进最好的 M3 配置后，同样能在 64K 拿到端到端提速。
- 单卡 H100 上 dense 能跑的上限约 95–98K token，所以端到端最优目前停在 64K。

**【讲者备注】**
- **M2c R6 DP −ln2：** 均值 V 用 M2c 的 pooled-compact 近似，其余同 M3 R6 DP −ln2。
  - 收据核对：pooled 均值构建次数等于 DP 选块次数；M3 那一组为 0。
  - 32K 上都不显著；精度都在噪声内。
- **96K：** 84–104K 的 12 题里：
  - 提示 ≤ 95,074 token 的 6 题所有方法都能跑；
  - ≥ 98,282 token 的 6 题连 dense 都在预填充时 OOM；
  - 128K 第一题就全部 OOM（已分配 76.7 GiB 时再申请 1.38 GiB 失败）。
  - 更长的上下文要用分块预填充或多卡，对 dense 和稀疏都一样。
- **协议与数据：** `v27_long_lb_m2_c1`、`v27_long_lb96k_c2`，`m2_panel_c1/`、`lb96k_panel_c2/`。

## P6　结论与下一步（30 秒）

**【正文】**
- **能说的：** 在最快的官方 dense 基线上，64K 端到端快约 13%，精度不降；原版都更慢。
- **要如实说的：**
  - 速度上与 SparseD 撞车；
  - AIME 上任何注意力稀疏都没有提速空间；
  - 高稀疏度下我们的选块不如 SparseD。
- **下一步：**
  - 查清高稀疏度下风险 top-k 为什么不如 SparseD；
  - 更长上下文要先解决单卡预填充的显存问题；
  - 与同学的 query 自适应保护能否结合（合作内容）。
