# V29 32K cost audit and independent diagnostic — 2026-10-02

This document separates measured facts, source-level costs and hypotheses. It adds no performance result. The V28 preview, its finalizer and the parent V18b deployment are unchanged. New code is limited to `scripts/v29_vllm_cost_profile.py` and its CPU tests; no shared runner, adapter or mathematical core is edited.

## What the existing results establish

The completed V18b interpretation (`docs/V18B_INTERPRETATION_V28_20261002.md:28–65`) reports 32K main/default-dense S/N **1.0302** [1.0198, 1.0413], while main/default-dense N is **0.7377** and S is **0.7600**. On the much smaller matched-native control subset, main/native S/N is **0.9862**, while N is **1.1778**. These are different populations and references: subtracting their ratios does not identify a causal overhead. Main/all-kept W is also not a selector-cost measurement because trajectories and counts differ.

S/N is the entire decode span divided by actual denoising forwards. Its numerator includes encoder commits, scheduling/host waits, request tails and adapter work, while its denominator excludes commits. Less denoising per canvas can amortize unchanged canvas costs over fewer denoising forwards. This is a possible explanation of an amortized ratio, not evidence that each denoising kernel became slower or that a specific component caused the observed 3% difference. Actual N must retain executed-but-unretired work; scheduler-consumed N is not interchangeable.

The existing 32K aggregate mean counts make this confounding concrete: main mean C/N is `15.2604 / 206.9688 ≈ .07373`, versus dense `17.2188 / 304.4062 ≈ .05656`, about **30% more commits amortized per main denoising forward**. These are ratios of marginal mean counts, not the panel's paired geometric-mean S/N estimate, an interval, or a measured commit-cost fraction. They show why S/N +3% cannot by itself establish a slower denoising forward/kernel or attribute the gap to sparse selection.

The historical HF GLOBAL/LOCAL shares in `docs/RESEARCH_CONTEXT.md` are useful context but do not establish native-vLLM composition. `scripts/v27_forward_attribution.py` and `scripts/v27_time_breakdown.py` profile HF forward/loop paths. `scripts/v27_vllm_adapter_overhead.py` uses a synthetic dense call with `causal=False, num_splits=1`; current native dense uses an effective dynamic-causal split-KV path. Its timings cannot be treated as matched costs against the current strongest dense reference.

## Minimal independent diagnostic

`scripts/v29_vllm_cost_profile.py` wraps the existing V28 qualification/benchmark worker in a **separate diagnostic process and new run directory**. It retains frozen binding/config validation, native sampling, graph/compile receipts, actual async execution counts and the existing request-boundary synchronizations. It does not add a device/event synchronization to `engine.step` or insert instrumentation into a formal worker.

Only one selected request is profiled. Earlier requests and engine initialization are unprofiled. The default zero-based ordinal is 1, so a binding containing one 32K cell yields one unprofiled warm request followed by the profiled request. A frozen diagnostic binding must contain only prompts in the existing 28–40K bin; it must provide a sufficient schedule and the selected control index where relevant. For larger bindings, choose the ordinal from the known frozen warm/schedule order instead of assuming ordinal 1 is timed or fully warmed. Do not truncate native stopping or reset RNG to produce a convenient profile.

The diagnostic attaches fixed `record_function` labels for:

- Decoder GLOBAL/LOCAL attention, with unknown/encoder layers explicitly separate.
- New KV-buffer construction versus canvas refresh.
- Alias consumer and split-list construction.
- Core selector and observation paths, native sample step and method begin/observe.
- The complete installed prepare hook, including its metadata read and original preparation.

The last range does not isolate the D2H transfer by itself. The report separately counts observed host synchronization calls, scalar extraction, copy enqueue, CUDA launch and allocator calls, grouped by nearest diagnostic range. Copy enqueue time is not host waiting; a scalar extraction is not by itself a measured transfer direction. Raw CUDA events recognized as DtoH are reported separately. No raw operator/kernel names, private inputs, traces, model values or completions are exported in the anonymous summary.

For native-hook/all-kept/main, attention tags also distinguish `denoise_*` from `encoder_*` by reading the adapter's already-existing exact CPU `step_ctx` after its normal metadata hook. This adds no GPU read. Encoder layers with unknown geometry remain `encoder_attention_other`; the diagnostic does not assume decoder GLOBAL indices classify encoder layers. Default dense has no adapter phase receipt and remains unclassified by phase where unavailable. Do not infer dense commit/denoise shares from late scheduler-consumed state or add a new synchronization to manufacture that split.

Directly attached kernel records are attributed to their nearest CPU range exactly once. Inclusive parent/child range durations are reported as inclusive, not summed into mutually exclusive parts. Raw CUDA activity duration and CPU-associated kernel duration are separate totals; the implementation does not presume equality. Activity can overlap across streams and profiler association can be incomplete. CPU self time versus inclusive wait time is also separated. These observations narrow a hypothesis; they do not compute a causal percentage of unprofiled S/N.

FULL graph replay may bypass the eager attention wrappers. The summary explicitly lists missing GLOBAL/LOCAL eager scopes rather than reporting their absence as zero attention cost. Default-dense profiles can still expose request CUDA activity, but a complete default-dense layer attribution may require a separately validated graph-aware tracing tool. Keep the default dense reference and matched PIECEWISE native-hook/all-kept/main profiles; do not relabel a forced-eager or PIECEWISE profile as default dense performance.

The profiler closes only after the existing request-boundary sync and PhaseTracker finalization. The profiler itself has overhead and may synchronize internally. All records emitted by this worker therefore remain private diagnostic records and must **never** enter a formal timing/quality summary. The anonymous diagnostic summary states `performance_claim_allowed=false` and `quality_evaluated=false`. No GPU profile has been run yet.

## Fair incremental directions

The root agent is preparing an opt-in fused paged-KV gather/copy candidate. It can apply equally to all-kept and main, while native/default dense remain their unmodified references because they do not use adapter copies. Require exact K/V equality on actual interleaved/random page layouts and the same sampler/support/clock before measuring it. A positive copy microbenchmark alone is not an end-to-end gain.

Two smaller candidates are worth locating with the diagnostic before implementation:

1. Cache per-canvas alias table/used-length metadata where its identity and immutability can be proven. Apply to every eligible all-kept/main consumer, retaining split-list build receipts. Request/epoch/canvas/length and page-table content/version matter; pointer equality is insufficient. Native's existing metadata may already avoid these allocations, so do not add synthetic native overhead to make the comparison match.
2. Reduce Python metadata preparation overhead where CPU values are already exact. Apply a valid shared change to native-hook/all-kept/main and preserve default dense as the strongest reference. The exact phase/step/sequence tuple is currently GPU state; replacing it with an upper bound or a late async count is unsafe. No synchronization-removal optimization is implemented here.

There is currently no evidence supporting further regroup deployment: the existing Torch held test and standard Triton permutation call are negative. Do not change timing conventions to erase those results. LOCAL attention, sampler and graph optimizations require the same eligible improvement in native references; they cannot be credited as a sparse-method gain.

CPU checks cover buffer classification, layer/available exact phase scope, nearest-range attribution, nested-range double-count avoidance, DtoH/host-wait distinctions, invalid duration/ancestry rejection, missing graph scope reporting, actual versus consumed execution counts, request selection/lifecycle and restoration on errors. Command: `python -m unittest tests.test_v29_vllm_cost_profile -v`. Eleven checks pass in the local dependency-light runtime. GPU/CUPTI availability and runtime profiling receipts remain unqualified until the independent frozen diagnostic is launched.
