# 稀疏为何没稳定赢 matched native，以及下一步实测

2026-10-03，US Central（UTC−5）。这是证据解释和新实验协议，不是新性能结果。

## 先分清总耗时与每步耗时

已有 V18b matched-native 子集只有每个长度 4 道题。其配对几何平均如下：

| 长度 | main/native 的 W | S/N | N |
|---|---:|---:|---:|
| 32K | 1.1377 | 0.9862 | 1.1778 |
| 64K | 1.0065 | 0.9137 | 1.0982 |
| 96K | 1.0446 | 0.8504 | 1.2810 |

这里每步已有收益，但步数增加抵消了它。W 包含 prefill；S 是生成时间，
N 是实际去噪 forward 数，S/N 是摊销时间，含调度和 commit 的影响。
不能把 W 的上升直接解释成稀疏 kernel 更慢，也不能把 N 的变化直接解释成
方法必然多走步：题目少，seed 与数值路径都改变轨迹。正在跑的三套正式面板
让四个对照覆盖全部题目、8 个 engine seed，再按题目聚类报告不确定性。
来源：[V18b 解释](V18B_INTERPRETATION_V28_20261002.md)、
[V28 小面板](V29_V28_PREVIEW_INTERPRETATION_20261002.md)。

独立诊断 003 中，native/all-kept/main 的 GLOBAL 事件区间/N 分别是
4.494699/4.894036/4.329062 ms；LOCAL 是6.461866/6.618996/6.611120 ms。
main 的 GLOBAL 省下约0.166 ms/N，并不等于整个模型省下相同比例。
这三次请求 N 不同、轨迹不同，事件本身也有开销，因此不作为因果归因或正式
速度比较。仅改5个GLOBAL层，25个LOCAL层、MoE、调度与commit仍须执行。
来源：[完整诊断及原始测量](../results/v29_20261002/cost32k_events003/README.md)。

## 现在追加的三个实验

1. **同态成本对照。** 固定同一份Q/K/V、stride、scale=1、长度和预定掩码，
   使用官方dynamic-causal/自动split路径对照adapter all-kept和稀疏消费者。
   对all-kept和稀疏同时比较原版与融合copy/merge；分别测完整调用、叶项和
   同态dense输出/融合观测，不将重叠叶项相加。合成输入只说明组件能力，
   不冒充真实请求慢因。先通过固定容差数值检查，再进行交替顺序计时。
2. **真实模型工程融合资格。** 三套任务分别准备legacy与fused的新协议，
   frozen main不变；fused把copy和merge后端都切到Triton，并同样作用于
   all-kept/main。每个数据集最长输入、四臂、一次warm和一次timed，共
   40条timed资格请求。只有完整路径、计数、数值布局、无计时JIT/capture和
   原评分流程通过后，才决定请求面板；资格结果不用于声称精度不降或加速。
3. **稀疏原地query置换。** 三份已有held状态分别仅移动84/103/78个query行，
   总行数4096；旧实现却搬整个Q。新组件只处理非平凡置换cycle，保持已有
   order/support，配合已有融合输出还原。保守计时包含正向置换、消费者、
   同样的融合合并及逆置换恢复。先验证Q完全恢复、对应掩码数值正确和有限，
   再看能否超过自然顺序的匹配融合参考。记录cycle打包、上传、构造成本及
   break-even复用次数；已有离线CPU求order约秒级，不能视为免费在线操作。

regroup与Haowei/CHW方向重叠，继续标为合作候选；同学分支只读，未吸收实现。
当前新增工作属于独立组件/资格准备，不修改正在运行的正式main。

## 执行边界

三台GPU目前用于完整正式面板。新代码先完成CPU检查并commit/freeze；新GPU
实验须等待当前正式生成和串行评分结束，再检查GPU空闲、使用新的独立run目录。
所有失败、负结果和资源用时保留；组件阳性不等于请求阳性。生成步数与任务
正确率问题另由完整配对面板回答，不能通过挑seed或仅报S/N绕开。
