## 0. 一句话

消融大部分已经做完。真正的风险有两处：
1. "按去噪进度决定何时重看"是否真比"按步号或周期"更好；
2. DyLLM（已官方支持 DiffusionGemma）在我们模型上的表现。

两者都要靠实验回答，接下来三天优先做。

## 1. 当前方法（最终候选）

- DiffusionGemma-26B，vLLM + FA4，H100。
- 只稀疏 5 个 GLOBAL 层的前缀 attention，预算 8192 token。
- 每个 canvas 第 1 步做 kernel 内精确观测，按"每个 head × 128 行块"选相同数量的 tile（保证 CTA 负载均衡），之后保持这份选择。
- 去噪进度（Junyu 的 C gate"已定程度"）到阈值时，重新观测一次整个前缀并重选，带粘性（已选 tile 有加分）。
- 所有速度都对比修复后的 dense（FA4 LOCAL 窗口 bug 已修，输出逐位相同）。

## 4. 论文定位（MLSys）

定位为一个系统工作："DLM 长上下文稀疏 attention 在真实服务栈里怎么做对"。贡献点：
1. **在官方自适应停止下控制步数：**
   - 已有工作都用固定步数；
   - 组内数据显示，稀疏会让步数膨胀 24–97%（Junyu 的报告、megakernel 的 slides）；
   - 我们的方法总步数不多于 dense。
2. **按去噪进度重看整前缀 + 粘性：** 有第 2 节的完整消融链，外加待补的决定性消融。
3. **和 FA4 协同设计：** 负载均衡的选择单元、kernel 内顺带观测（不额外跑一遍）、单波次 grid。
4. **端到端评测和系统发现：**
   - vLLM 里报端到端 W 和纯 decode 时间 S（LoSA 只报前缀 attention 延迟）；
   - FA4 LOCAL 窗口 bug 的根因与修复（修复后 dense 的 decode 快 1.3–1.5 倍）；
   - 速度上限分析：prefill 占比、只稀疏 GLOBAL 层时的理论上限、随上下文增长的趋势。

**现有速度**（最终方法，相对修复后 dense，S1）：
- 128K 时稀疏 attention kernel 约快 14 倍；
- 100–120K 时每步约快 1.4 倍；
- 长输出任务纯 decode 快 1.1–1.5 倍，端到端快 1.1–1.3 倍。

**公平性：**
- 同一部署，每个 cell 在同一台机器，同题同 seed。
- 三档预算：各方法原文预算、等保留量（8192 token）、等实际工作量（dense 和观测调用都计入）。
- 同时报 W、S、prefill、总步数 N、每 canvas 步数、单步时间。

## 6. 接下来三天（UTC−5）

1. **"何时重看"的决定性消融（最优先，约 4 小时 GPU）：**
   - 同样重看 1 次，在三种时机重看：固定步号（取按进度触发时的平均步号）、固定周期、按进度触发；
   - 四个数据集都跑；
   - adapter 需要加"固定周期"选项，约半天。
2. **DyLLM：** CPU 上先搭环境；GPU 有空档就在我们的子集上跑，并和它自己的 dense 以及我们的结果比较。
3. **移植基线：** 先移植 SparseD、Sparse-dLLM、Quest，再做 LoSA。
4. **seed 3–4 验证（已在 GPU 上跑）：** 最终方法和"已接受比例"时钟的对照。

**判断点：**
- 第 1 项如果显示"按进度触发"明显更好，这就是核心 novelty。
- 如果不比固定步号或周期好，就承认时钟不是关键，把重心放在贡献 1、3、4。
